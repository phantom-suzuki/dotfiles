## 0. 目的と推奨構成

本機構は、Claude Code の transcript を削除する前に、再利用できる知識とその根拠を保存する。

本機構は、次の三つを生成する。

| 成果物 | 本機構が保存する内容 |
|---|---|
| 永続メモリ | 本機構は、今後も適用する方針、判断、再利用可能な解決方法を保存する。 |
| セッション記録 | 本機構は、その会話の判断経緯、却下案、未解決事項、約束を保存する。 |
| 根拠・処理台帳 | 本機構は、原文抜粋、出典、検証結果、処理範囲、削除可否を保存する。 |

推奨構成は、**永続キューと単一ワーカーによる非同期処理**とする。機械処理が入力を整理し、LLM が意味を抽出する。別の検証段が原文との対応と取りこぼしを確認する。

本機構は、圧縮率よりも重要情報の保持を優先する。検証できないログは削除対象にしない。

本書の数値上限と品質基準は、実装時に検証する初期設計値である。本調査は、その性能を実測していない。

[precompact-snapshot.py](/Users/h-suzuki/.claude/hooks/precompact-snapshot.py) は、次の処理を行っている。

- hook は、session ID、cwd、transcript のパス、起動理由を受け取る。
- hook は、branch と変更ファイルを取得する。出力する変更ファイルは最大50行である。
- hook は、transcript 全体を行単位で走査する。
- hook は、ユーザー発言の先頭280文字を蓄積する。出力する発言は末尾6件である。

## 2. 何を残し、何を捨てるか

### 2.1. 保存先を先に分ける

本機構は、各情報について「将来の行動を変えるか」と「そのセッションだけで有効か」を判定する。

| 情報 | 本機構の扱い |
|---|---|
| ユーザーが明示した継続的な方針・禁止事項 | 本機構は、適用範囲と例外を伴う永続メモリ候補にする。 |
| ユーザーが選んだ設計と、その理由 | 本機構は、決定を保存する。却下案は、選ばなかった理由と再検討条件を残す。 |
| つまずきと解決 | 本機構は、症状、発生条件、原因の確度、対処、確認結果を一組で保存する。 |
| 約束・未完了の依頼 | 本機構は、担当者、対象、期限、条件、状態をセッション記録に残す。 |
| 未解決の疑問・仮説 | 本機構は、未解決であることを明記する。確定事実として登録しない。 |
| 一時的な branch・変更ファイル | 本機構は、作業再開に必要な間だけセッション記録に残す。 |
| 大量のツール出力 | 本機構は、判断や検証の根拠に必要な部分を抽出する。 |
| 重複した進捗報告、挨拶、同じ出力の再掲 | 本機構は、他の情報を失わないことを確認して省く。 |
| 内部思考、usage、描画・通信上の補助情報 | 本機構は、知識本文から除外する。必要な処理情報だけ台帳に残す。 |
| 認証情報や秘密値 | 本機構は、知識本文とLLM送信内容から除外する。 |

本機構は、保存価値の判断をキーワードだけで行わない。「今後」「禁止」と書かれていない訂正や短い承認も、前後の会話と合わせて判定する。

### 2.2. 発言の権限と事実性を分離する

各候補は、少なくとも次の区分を持つ。

| 区分 | 本機構が区別する意味 |
|---|---|
| ユーザーの明示決定 | ユーザー本人が、対象と範囲を示して決めた。 |
| アシスタントの提案 | アシスタントが提案したが、採用は確認できない。 |
| 観測結果 | ツール結果などが、特定時点の状態を示している。 |
| 推測・未確認報告 | 発言者が推測したか、裏付けが不足している。 |
| 引用・再注入・代理入力 | 外部文書、過去要約、hook、子ログなどから持ち込まれた。 |

本機構は、アシスタントの「完了しました」だけで約束を完了にしない。ツールの成功結果、成果物、ユーザーの確認などを関連付ける。裏付けがなければ「完了報告あり・未検証」とする。

本機構は、ユーザーの無反応を承認と解釈しない。「それで進めて」は、何を指すかを特定できた場合だけ決定にする。

本機構は、子ログ内の user ロールを、そのまま実ユーザーの発言にしない。子ログの入力は、委譲された指示である可能性を保持する。

### 2.3. ツール出力から残す情報

機械処理は、ツール名、呼出しID、結果ID、終了状態、対象、エラー、検証値を抽出する。意味抽出段は、それらを会話中の判断に結び付ける。

例えば、本件では次の知識を残す。

- 調査は、109MB の transcript の一括読み込みで、1,070MB のメモリ消費を確認した。
- 修正は、読み込み対象を末尾に制限した。
- 再発防止策は、ファイル全体と巨大な1行の両方に対して、メモリ上限を設けることである。

本機構は、ログが6.7GBあったという事実だけから、6.7GBがそのままメモリに載ったとは推論しない。

また、本機構は「失敗後に成功した」という時系列だけで、直前の変更を原因解決と断定しない。

### 2.4. 根拠を原文削除後も残す

各知識は、次の情報を持つ根拠レコードに接続する。

- 根拠レコードは、project ID、session ID、イベントIDを保持する。
- 根拠レコードは、入力世代のハッシュ、行番号、バイト範囲を保持する。
- 根拠レコードは、話者、時刻、適用範囲、必要な原文抜粋を保持する。
- 根拠レコードは、承認の対象となった提案や、後続の撤回も関連付ける。
- 根拠レコードは、秘匿処理の有無を記録する。

パスやハッシュだけでは、削除後に内容を読めない。本機構は、知識を支える抜粋そのものを保存する。

ハッシュは、保存データの同一性を確認するために使う。ハッシュは、発言の真偽や外部に対する真正性を証明しない。

## 3. 圧縮パイプラインとモデル選定

### 3.1. 段構成

| 段 | 処理主体 | 処理内容と出力 |
|---|---|---|
| 0. 発見・保全 | 機械処理 | 処理対象を列挙する。入力世代を識別し、復元可能な保全コピーを作る。 |
| 1. 構文解析 | 機械処理 | JSONL をストリーミング解析する。イベント、出典、関連IDをディスク上の台帳へ記録する。 |
| 2. 正規化・分割 | 機械処理 | 重複、本文、ツール結果、再注入を区別する。上限付きの意味抽出用チャンクを作る。 |
| 3. 知識候補の抽出 | Sonnet 5 | 決定、理由、訂正、失敗と解決、約束を根拠付きで抽出する。 |
| 4. 時系列・既存知識との統合 | Sonnet 5 | 同じ主題を照合する。新規、補強、更新、撤回、競合に分類する。 |
| 5. 根拠・漏れの検証 | 機械処理＋Opus 5 | 出典を照合する。原文側から重要情報を再点検する。 |
| 6. 公開 | 機械処理 | 検証済みのメモリ、セッション記録、根拠を公開する。 |
| 7. 削除適格性の判定 | 機械処理 | 入力の不変性、処理完了、公開状態、保全状態を照合する。 |

モデル名は、調査時点の公式一覧にある `claude-sonnet-5` と `claude-opus-5` を初期候補とする。利用可能なモデルIDと能力は、運用開始時にも確認する。[Anthropic のモデル一覧](https://platform.claude.com/docs/en/models/overview)

### 3.2. 機械処理は意味情報を先に捨てすぎない

機械処理は、人の発言とアシスタントの公開回答を、意味抽出段に一度は渡す。機械処理は、キーワードに一致しないという理由で発言を落とさない。

同じイベントIDの重複でも、内容が異なる場合は除去しない。APIメッセージが同じでも、別の content block は保持する。

チャンクは、会話の順序とイベント間の参照を保持する。1チャンクは入力16,000トークンを目安とし、バイト数にも上限を設ける。長い発言は連続した区間へ分割する。

本機構は、承認、tool use と結果、失敗と再試行をIDで関連付ける。隣接チャンクの重なりだけに依存しない。関連情報が上限内に収まらなければ、複数回に分けて照合する。

各イベントは、「候補に反映」「規則により除外」「保留」のいずれかになる。解析不能や不明なイベントを、処理済みとして黙って捨てない。

### 3.3. 自由文の再要約を繰り返さない

LLM は、最初に知識候補を構造化して返す。候補は、主張、話者、状態、適用範囲、根拠ID、関連する決定IDを持つ。

統合段は、この候補と根拠を扱う。前段の短い要約だけを何段も再要約しない。文章としての整形は、検証後に行う。

この構成は、段を重ねるたびに条件や否定が失われる問題を抑える。

### 3.4. モデル選定の理由と代替案

| 選択肢 | 推奨とトレードオフ |
|---|---|
| Sonnet 5 で抽出し、Opus 5 で検証する | 本案は、この構成を推奨する。大量の抽出処理と、重要な判定の検証を分担できる。品質は評価で確認する。 |
| 全段を Opus 5 にする | 本案は、比較評価用に採用する。費用と処理時間は増える。同じモデルによる共通の誤りは残る。 |
| Haiku 4.5 で事前選別する | 本案は、初期版では採用しない。安価でも、抽出前の取りこぼしは後段で回復しにくい。 |
| ローカルLLMを使う | 本案は、対象Macでは採用しない。モデル常駐がメモリ削減の目的と競合する。 |

本機構は、ツール権限のない固定用途のAPI呼出しを使う。Claude Code の作業セッションや子エージェントを大量起動しない。

本機構は、モデルID、プロンプト版、生成設定、応答、処理版を記録する。モデルが利用不能になった場合は停止する。未評価のモデルへ自動で切り替えない。

## 4. 精度の担保と再現可能な評価

### 4.1. 「高精度」の定義

本案は、高精度を「もっともらしく短い文章」と定義しない。本案は、次の指標で測る。

| 指標 | 測り方 | 初期合格基準 |
|---|---|---:|
| 主張の適合率 | 保存した主張のうち、根拠が内容・条件・話者を支持する割合を測る。 | 99.5%以上 |
| 重要情報の再現率 | 正解集合の重要情報のうち、適切な保存先に残った割合を測る。 | 98%以上 |
| 重大情報の保持 | 明示禁止、撤回、未完了の約束、適用範囲を個別に確認する。 | 評価集合で欠落・誤り0件 |
| 根拠の参照整合性 | 全主張の根拠IDと保存済み抜粋を照合する。 | 100% |
| 更新判定の安全性 | 競合を誤って上書きした件数を測る。 | 評価集合で0件 |
| 利用時の回答品質 | 圧縮結果だけで過去判断に関する質問へ答えさせる。 | 重要設問で誤答0件 |
| 資源使用 | RSS、hook遅延、処理時間、API費用を測る。 | 第8節の上限内 |

これらは合格基準であり、現在達成している値ではない。有限の評価集合で誤りがゼロでも、未知のログに対する完全性は証明できない。

### 4.2. 正解データを作る

初期評価では、40セッション以上から1,000件以上の判定対象を作る。選定者は、次の条件で層別に選ぶ。

- 選定者は、小さいログと100MB級のログを含める。
- 選定者は、複数projectと既存の子ログを含める。
- 選定者は、撤回、条件付き承認、短い返答、長距離の参照を含める。
- 選定者は、ツール出力に埋もれた重要情報を含める。
- 選定者は、秘密値、要約の再注入、未知のイベント、壊れた行を含める。

評価者は、原文を区間ごとに読み、保存すべき情報と根拠を記録する。重要ケースは二者で独立に判定する。判定が割れた場合は、理由と採用した解釈を残す。

正解データには、候補の有無だけでなく、話者、状態、範囲、保存先、更新関係を含める。

### 4.3. 再現性を確保する

評価セットは、入力ハッシュ、対象範囲、匿名化版、正解ラベル、採点規則を固定する。関連する会話と子ログは、同じ分割へ入れる。調整用と最終評価用のデータを混ぜない。

評価は、同じ入力に対して3回以上行う。報告は、件数、割合、ばらつき、重大な誤りを示す。生成設定を固定しても、完全に同じ応答になるとは仮定しない。

比較対象は、機械抽出だけ、単純なチャンク要約、本案の三つとする。圧縮率と費用は、品質基準を満たした構成同士で比較する。

### 4.4. 運用中も原文側から検証する

検証段は、候補から根拠を見る検証と、原文から候補を見る検証を分ける。

前者は、誤った主張を見つける。後者は、抽出されなかった重要情報を見つける。検証用LLMは、抽出用LLMの自己評価を合格理由に使わない。

初期運用では、人が保存結果と削除対象一覧を確認する。安定後も、全件の機械検証とLLM検証を続ける。人による抜取確認は補助とし、重大な欠落が見つかれば、影響する処理版の削除適格性を停止する。

## 5. 既存 memory 形式との統合

### 5.1. 読取互換性を保つ

読取処理は、`metadata.type` とトップレベルの `type` の両方を受け付ける。両方が存在して値が違う場合は、競合として扱う。

新規メモリは、`name`、`description`、`metadata.type` を使う。既存メモリの更新では、そのファイルの形式と未知のフィールドを保持する。初期導入で全メモリを一括変換しない。

複数セッションの根拠は、既存の `originSessionId` 一つへ押し込まない。本機構は、別の根拠台帳で多対多の対応を管理する。

### 5.2. 保存先を分離する

| 保存先 | 役割 |
|---|---|
| 各projectの既存 `memory/` | 本機構は、継続的に使う知識と索引を公開する。 |
| `~/.claude/knowledge-compiler/records/` | 本機構は、セッション記録と判断履歴を保存する。 |
| `~/.claude/knowledge-compiler/evidence/` | 本機構は、原文抜粋と出典を保存する。 |
| `~/.claude/knowledge-compiler/state/` | 本機構は、キュー、処理台帳、公開履歴を保存する。 |
| `~/.claude/knowledge-compiler/vault/` | 本機構は、検証が終わるまで復元可能な原文を保管する。 |

これらは新設候補のパスである。本調査は、ディレクトリを作成していない。

本機構は、全projectの知識を work の memory に集約しない。保存先は、確認できたprojectと適用範囲から決める。project名のパス表現だけから、Org全体への適用を推定しない。

### 5.3. 重複と更新を判定する

検索処理は、適用範囲、対象、主題、固有名、正規化した主張で候補を絞る。初期版は、ディスク上の全文検索を使う。LLMは、絞り込んだ候補と原文の関係を判定する。

| 判定 | 本機構の処理 |
|---|---|
| 同じ意味で同じ範囲 | 本機構は、本文を増やさず、根拠を追加する。 |
| 同じ知識への補足 | 本機構は、既存の知識単位へ理由や適用条件を追加する。 |
| 明示的な変更・撤回 | 本機構は、現行本文を更新し、旧版と変更理由を履歴へ残す。 |
| 独立した知識 | 本機構は、新規ファイルと索引の1行を作る。 |
| 範囲が異なる例外 | 本機構は、例外条件を明示して区別する。 |
| 矛盾するが優先関係が不明 | 本機構は、既存本文を変更せず保留する。 |

本機構は、「新しい発言だから正しい」とは判定しない。話者、適用範囲、変更の明示、時間的な有効性を確認する。

既存メモリがスキルや別文書を正本として示している場合は、そのポインタを保つ。例えば、Slack文体メモリは正本の所在を示している。本機構は、その規範を別のメモリへ複製しない。

### 5.4. 本文と索引を安全に公開する

公開処理は、メモリ本文、索引、根拠、履歴を一つの公開計画にまとめる。

公開処理は、既存ファイルのハッシュを確認する。検討中に人やClaude Codeが編集していた場合は、再照合する。古い内容を基に上書きしない。

単一ファイルの置換は原子的に行う。ただし、複数ファイルの置換全体が原子的だとは扱わない。処理台帳は、途中停止から再開または復元できる情報を保持する。

公開処理は、本文を先に配置し、索引を最後に更新する。全ファイルとリンクを読み直してから公開完了を記録する。原文削除は、その後にだけ判定する。

## 6. hook 統合と非同期キュー

### 6.1. 実行タイミングを分ける

| タイミング | 本機構の役割 |
|---|---|
| PreCompact | hook は、現在の到達位置とsession情報を短いジョブとして登録する。 |
| PostCompact | hook は、既存の再注入を行う。新しい圧縮結果の完成を待たない。 |
| セッション終了時 | hook は、最終走査の候補を登録する。終了イベントだけでは原文不変を保証しない。 |
| 定期走査 | ワーカーは、hookが届かなかったログと既存ログを発見する。 |
| 削除操作の前 | 判定処理は、最新世代の全文処理と公開完了を確認する。 |

PreCompactのスナップショットは、短期的な作業再開用として維持する。意味圧縮は、別のワーカーが行う。

推奨する通常運用は、セッション終了後の処理と、Macのメモリ状態が良い時間帯の定期処理である。実行中セッションの増分処理は認めるが、その結果で原文全体の削除を許可しない。

### 6.2. キューを永続化する

hookは、本文をキューへ入れない。hookは、session ID、project ID、入力パス、観測サイズ、更新時刻、要求理由だけを登録する。

キューは、登録内容を永続化してから成功を返す。登録に失敗しても、通常のcompactionは止めない。定期走査が未登録の入力を補う。

ワーカーは、次の規則に従う。

- ワーカーは、同一sessionの未処理要求を最新の到達位置へまとめる。
- ワーカーは、全projectを通じて一度に一つだけ処理する。
- ワーカーは、期限付きの処理権とハートビートを記録する。
- ワーカーは、停止した処理を最後の確定済み区間から再開する。
- ワーカーは、再実行でも同じメモリを重複作成しない。
- ワーカーは、再試行回数とAPI費用に上限を設ける。

公式の非同期hookは、発火ごとに別プロセスを起動し、発火間の重複を排除しない。本案は、hookから短い登録だけを行い、外部の単一ワーカーへ処理を集約する。[Claude Code の非同期hook仕様](https://code.claude.com/docs/en/hooks#run-hooks-in-the-background)

### 6.3. 既存hookの負荷も抑える

将来の統合では、PreCompactのユーザー発言保持を末尾6件の固定長にする。入力走査も末尾の上限付き区間、または別途更新したキャッシュへ変える。範囲内に6件なければ、取得できた件数だけを使う。

gitの出力取得にもサイズ上限を設ける。同期hook全体には時間予算を設け、予算内に得られた情報だけを残す。

PostCompactは、`CONTEXT.md` とスナップショットを上限付きで読む。全文を読んでから文字列を切り出さない。

### 6.4. 再注入は検証済みの情報に限定する

初期版は、コンパイラの結果をPostCompactへ自動追加しない。永続メモリと必要時の参照を先に安定させる。

追加する場合は、同一session・同一projectの検証済み情報から、未解決事項や継続中の判断だけを選ぶ。追加量は2,000文字以内を初期値とし、既存の再注入内容と合算した上限も持つ。

現在の注意書きは raw transcript の照合を要求している。原文削除後の参照には、保存済み根拠への案内が必要になる。保存済み根拠もない指示は実行しない。

また、**過去の承認は、新しい操作への包括的な許可にはしない**。再注入した記録は、過去の判断を説明する資料として扱う。

## 7. 失敗時の安全性と削除条件

### 7.1. 入力世代を固定する

本機構は、パスだけで処理済みを管理しない。入力世代は、ファイル識別情報、長さ、ハッシュで区別する。

実行中ログは、完全な行が終わる位置までを増分処理する。不完全な末尾は次回へ持ち越す。

ログが追記された場合は、新しい区間を処理する。既存部分が書き換わった場合は、新しい入力世代として扱う。過去世代の合格結果で新しい世代を削除しない。

親ログ、子ログ、根拠として必要な外部ツール出力は、依存関係を記録する。親が完了しただけで、子ログのディレクトリ全体を削除対象にしない。

### 7.2. 原文を先に保全する

本機構は、意味圧縮の前に、復元可能な原文コピーを `vault/` に作る。コピーは、ストリーミングによる可逆圧縮を使う。保存処理は、復元したバイト列のハッシュまで照合する。

この可逆圧縮は、知識抽出とは別の安全策である。知識抽出が失敗しても、原文を復元できる状態を維持する。

保全に必要な空き容量がなければ、ワーカーは処理を保留する。ワーカーは、空き容量を作るために未検証ログを消さない。

### 7.3. 状態を明示する

| 状態 | 本機構が保証する内容 |
|---|---|
| 発見済み | 本機構は、入力の存在を把握している。 |
| 保全済み | 本機構は、対象世代の原文を復元できる。 |
| 処理中 | 本機構は、一部の区間を処理している。 |
| 検証済み | 本機構は、対象世代の処理範囲と品質検証を完了している。 |
| 公開済み | 本機構は、知識、根拠、索引の公開整合性を確認している。 |
| 削除適格 | 本機構は、全削除条件を満たしている。 |
| 保留・失敗 | 本機構は、原文と保全コピーを削除しない。 |

「検証済み」は、意味の完全な保存を数学的に保証する状態ではない。定義した検証と保留条件を満たした状態である。

### 7.4. 削除適格性を機械判定する

原文の削除には、次の条件をすべて要求する。

1. 判定処理は、対象sessionが非稼働であり、再開や書込みがないことを確認する。
2. 判定処理は、サイズと時刻だけでなく、対象世代のハッシュを照合する。
3. 判定処理は、全入力範囲と必要な依存ファイルの処理完了を確認する。
4. 判定処理は、未知の構造、解析不能、未検証の省略が残っていないことを確認する。
5. 判定処理は、各知識の保存先と根拠が読めることを確認する。
6. 判定処理は、重要な競合や約束の状態が、解決済みまたは明示的な未解決として保存されていることを確認する。
7. 判定処理は、公開が完了し、途中状態でないことを確認する。
8. 判定処理は、具体的な削除対象とハッシュを記した一覧に、必要な実行承認があることを確認する。

現在の作業規約では、ファイル削除にユーザーの明示指示が必要である。したがって、初期運用は削除一覧の提示までを自動化する。削除の自動運用は、別途明示された許可範囲でのみ有効化する。

削除処理は、ワーカーから分離する。LLMの返答や終了コードだけで削除を実行しない。

原文の元パスを削除した後も、保全コピーを最低7日間保持する。保全コピーの最終削除時には、成果物の破損や検証取消しがないことを再確認する。失敗中の保全コピーには、期限による自動削除を適用しない。

### 7.5. Claude Code側の自動削除と競合させない

確認したユーザー設定には、`cleanupPeriodDays` の明示設定がなかった。ただし、本調査は全設定階層の実効値を確認していない。

公式資料では、transcriptなどは保存期間に応じた起動時の削除対象になる。コンパイラが削除しなくても、別の削除経路で原文を失う可能性がある。[Claude Code のデータ配置と自動削除](https://code.claude.com/docs/en/claude-directory)

導入時には、既存ログの初回保全を優先する。その間は、実効的な保存期間と起動時削除の挙動を確認する。通常の保管場所とは別の `vault/` が、自動削除の対象外であることも検証する。

本機構が保証できる保全範囲は、保全済みの入力世代である。発見前の外部削除までは保証できない。設定期間を延ばすだけで、失敗ログの無期限保全を保証したことにはしない。

### 7.6. 障害ごとの動作を固定する

| 障害 | 本機構の動作 |
|---|---|
| API障害・利用制限・費用上限 | ワーカーは、途中結果を確定せず待機または保留する。 |
| LLM出力の形式不正・途中終了 | ワーカーは、限定回数だけ再試行する。解消しなければ保留する。 |
| JSON破損・未知の構造 | ワーカーは、対象位置を記録し、その世代の削除を禁止する。 |
| プロセス停止・Mac再起動 | ワーカーは、確定済み区間と公開台帳から再開する。 |
| ディスク不足 | ワーカーは、新しい書込みを止める。未検証原文を残す。 |
| メモリ逼迫 | 監視処理は、投入を止め、必要ならワーカーを終了する。 |
| メモリ本文の同時編集 | 公開処理は、上書きを中止して再照合する。 |

## 8. 低メモリ設計

### 8.1. 全文読み込みを構造的に避ける

本件では、109MBの一括読み込みが1,070MBのメモリ消費につながった。入力文字列、行配列、解析結果、送信用文字列が重なる設計を避ける必要がある。

本機構は、入力全体の文字列化、全行の配列化、全候補のメモリ保持を禁止する。ディスク上の索引と途中結果を使い、必要な範囲だけを読む。

### 8.2. 巨大な1行も上限付きで扱う

「1行ずつ読む」だけでは不十分である。JSONLには、巨大なツール出力や添付を含む1行が存在し得る。

| 対象 | 初期設計値と処理方針 |
|---|---|
| ファイル入力バッファ | 読取処理は、64KiB単位で読む。 |
| 通常の1レコード | 解析処理は、1MiB以内でのみ通常のJSON解析を使う。 |
| 1MiBを超えるレコード | 解析処理は、ディスク退避と増分解析へ切り替える。 |
| 巨大な文字列・深い入れ子 | 解析処理は、文字列断片、深さ、要素数にも上限を設ける。 |
| LLMの入力 | 送信処理は、1要求を16,000トークンかつ256KiB以内にする。 |
| LLMの出力 | 受信処理は、本文サイズにも64KiBの上限を持つ。 |
| 検索・DBキャッシュ | 検索処理は、キャッシュ予算を固定する。全件を読み込まない。 |
| 並列処理 | スケジューラーは、ワーカー数と同時API呼出し数を1にする。 |

増分パーサーも、巨大な文字列を内部で一括確保する実装では条件を満たさない。実装時には、文字列内部まで分割できることを確認する。

対応できない巨大レコードは、保留にする。無言で切り捨てて削除適格にしない。

本機構は、画像やbase64を不用意に展開しない。画像だけに重要な判断根拠がある場合は、その画像を根拠として保全し、専用の確認が終わるまで削除を止める。

### 8.3. 合計メモリを監視する

初期目標は、監視処理、ワーカー、APIクライアントを合わせたRSSを通常128MiB以下にする。192MiBで新規処理を止め、256MiB超過で監視処理がワーカーを終了させる。

これらは運用上の停止閾値であり、監視周期の間も絶対に超えないという保証ではない。主要な防御は、各バッファと処理量の上限である。監視は最後の防御として使う。

ワーカーは、OSのメモリ圧力が高い場合に起動しない。実行中に圧力が上がった場合は、新しいAPI要求とチャンク処理を止める。短時間に再起動を繰り返さない。

APIクライアントは、送信前の全ログ結合や、過去応答の無制限保持を行わない。診断ログにも、transcript本文を複製しない。

### 8.4. 資源上限を試験する

資源試験は、次のケースを含める。

- 試験は、109MB級、135MB級、1GB級の入力を使う。
- 試験は、通常サイズの行を増やしても、ピークRSSが入力総量に比例しないことを確認する。
- 試験は、100MBの1行、長いユーザー発言、巨大な添付を含める。
- 試験は、末尾の書込み途中、壊れたJSON、深い入れ子を含める。
- 試験は、API再試行、通信停止、公開途中の終了を含める。
- 試験は、メモリ圧力とディスク不足を再現する。
- 試験は、コンパイラに関係する全プロセスの合計RSSを測る。

本機構は、入力総量を増やした試験だけで合格しない。最大レコード、関連付け件数、再試行回数を増やした場合も、上限が機能することを確認する。

## 9. 導入順序と完了条件

### 9.1. 導入を段階化する

| 段階 | 実施内容と次段への条件 |
|---|---|
| 1. 保全と評価データの準備 | 導入担当者は、既存ログを保全する。評価対象と実効的な削除設定を確認する。 |
| 2. 出力だけを作る試行 | コンパイラは、候補と根拠を作る。既存メモリの更新と原文削除は行わない。 |
| 3. メモリ統合 | コンパイラは、人が確認できる差分を作る。競合検出と途中復旧を検証する。 |
| 4. 削除適格性の運用 | 判定処理は、具体的な削除一覧を作る。承認済み対象だけを削除できる状態にする。 |
| 5. hook連携 | hookは、短いキュー登録を行う。定期走査と重複しても安全であることを確認する。 |

### 9.2. 設計上の完了条件

実装は、次の条件を満たした時点で初期運用可能と判定する。

1. コンパイラは、既存の二種類のmemory形式を読める。
2. コンパイラは、親ログと入れ子のログを漏れなく棚卸しできる。
3. コンパイラは、判断、理由、撤回、失敗と解決、約束を根拠付きで保存できる。
4. コンパイラは、品質評価と低メモリ試験に合格する。
5. コンパイラは、再起動と再実行で重複や誤上書きを起こさない。
6. 削除処理は、未処理、失敗、入力変更、公開途中の原文を削除しない。
7. 保存結果は、原文削除後も、重要な判断の内容と理由を説明できる。

## 10. 本調査の実施範囲

本調査は、指定された二つのhook、索引と9件のメモリ、transcriptの一部を読んだ。本調査は、JSONLの件数とサイズを再帰集計した。追加で、ユーザー設定の保存期間の有無とhookイベント名を確認した。

変更したファイルはない。実装、テスト、lint、commit、push、ログ削除は行っていない。

実装時に残る確認事項は、モデルの評価結果、実効的な自動削除設定、PostCompactへの実注入、資源上限の実測である。本案は、それらが未確認でも原文削除へ進まない構成とする。
