# 原案: Claude Fable 5.1

2026-09-15 に Claude Fable 5.1 が作成した原案。
統合版は `design.md`。この文書は出典として残している。

> 注: 本文中の「1 行の最大は 0.2MB」「MEMORY.md は 24,576 バイト上限」「xz で 8〜12 分の 1」は、
> 実測により誤りと判明した。訂正内容は `design.md` の 3.1 節にある。


結論: 会話記録（transcript）を「機械抽出 → LLM 抽出 → 既存 memory への統合 → 検証 → 削除許可」の 5 工程で処理し、処理を通った記録だけを消す。低メモリの鍵は「1 行ずつ読む」「LLM に渡す前に 3〜5% まで機械的に絞る」「LLM プロセスは同時に 1 本だけ」の 3 点。

| 項目 | 設計の要点 |
|---|---|
| 残すもの | ユーザーの決定（AskUserQuestion の回答）・方針・つまずきと解決・約束・参照先。既存のコンパクション要約を一次資料として再利用する |
| 捨てるもの | ツール出力・ファイル読み込み結果・thinking・attachment・キュー操作・課金メタデータ |
| 段構成 | 台帳登録 → 機械抽出（決定論的、Python 標準ライブラリ）→ LLM 抽出 → 統合 → 検証 → 削除許可 |
| 中間生成物 | 「ダイジェスト」（機械抽出の出力、元の 3〜5%）を恒久保存する。LLM が取りこぼしても grep で戻れる |
| 精度の測り方 | AskUserQuestion の回答を自動の正解データにする。事実ごとに原文引用を必須にして捏造を機械検出する |
| hook 統合 | PreCompact と SessionEnd はキューに 1 行書くだけ（10ms 台）。実処理は LaunchAgent のワーカーが直列で行う |
| 削除の安全 | 台帳の状態が `verified` でないファイルは絶対に消さない。消す前に圧縮アーカイブへ移す 2 段階 |

## 1. 前提として調べた事実

設計の根拠になる実測値。2026-09-15 時点。

| 観点 | 実測 |
|---|---|
| 総量 | `~/.claude/projects/` 6.7GB、JSONL 2,385 本。主セッション 590 本（4.3GB）、サブエージェント 1,797 本（約 2.4GB） |
| サイズ分布 | 主セッションの中央値 3.5MB、90 パーセンタイル 20MB、50MB 超が 8 本。1 行の最大は 0.2MB |
| 年齢 | 7 日以内 2.3GB、7〜30 日 4.2GB、30 日超はほぼ無し。Claude Code の既定の自動削除（30 日）が効いていると見える |
| 集中 | `wp-platform` 1 プロジェクトで 5.7GB（85%） |
| 中身の比率（109MB の統括セッション） | assistant 39MB（thinking と tool_use が主）、attachment 26MB（`queued_command` 11.8MB、`total_tokens_reminder` 3.8MB など全部ノイズ）、user 17MB、`queue-operation` 8MB |
| 大きなツール出力 | 本文に埋め込まず `<session-id>/tool-results/` に別ファイルで置かれる（17MB） |
| すでにある要約 | コンパクションごとに `isCompactSummary: true` のユーザー行が残る。1 本 12〜17KB、109MB のセッションに 18 本。見出しは Primary Request / Errors and fixes / Pending Tasks など 9 種で固定 |
| 決定の記録 | `AskUserQuestion` の tool_use（質問と選択肢）と tool_result（選んだ回答）が対で残る。ユーザーの決定を機械的に取り出せる |
| その他の高信号イベント | `ai-title`（セッション題名）、`away_summary`（離席時の進捗要約）、`last-prompt`、`file-history-delta`（編集したファイル） |
| 既存 memory の規模 | `wp-platform` の memory は 1,370 本。`MEMORY.md` は 24,567 バイトで上限 24,576 バイトに達している。`index_*` で分割索引を運用中 |
| frontmatter のばらつき | `type:` を最上位に書く古い形式と `metadata.type:` の新形式が混在。`originSessionId` を持つものがある |
| hook の非同期化 | 公式プラグインが、stdout の 1 行目に `{"async": true, "asyncTimeout": ms}` を出して hook をバックグラウンド化している（`security-guidance/hooks/ensure_agent_sdk.py`） |
| 使える道具 | Python 3.14、`jq`、`claude` 2.1.272（`-p` モードあり）、`mem-guard`（空きメモリ監視、120 秒ごと）、`session-sweep` |

設計に効く含意は 3 つ。

- 削除は既に Claude Code が 30 日で行っている。圧縮が間に合う前に消えるので、`cleanupPeriodDays` を明示的に長く（例: 90 日）設定し、削除の主導権をこの機構に移す（設定名は導入時に公式ドキュメントで確かめる）
- 長いセッションほど、コンパクション要約という「Claude 自身が書いた一次要約」が揃っている。ゼロから要約し直すより、これを土台にしたほうが安く正確になる
- `MEMORY.md` は満杯。圧縮結果を 1 事実 1 行で索引に足す設計は成立しない。分割索引が前提になる

## 2. 何を残し、何を捨てるか

### 2.1 判断の軸

「あとで別のセッションが同じ調査をやり直す・同じ判断を蒸し返す・同じ穴に落ちる」ことを防ぐ情報だけを残す。再生成できるもの（ファイルの中身、コマンド出力、探索の途中経過）は捨てる。

### 2.2 イベント別の扱い

| 階層 | 対象 | 扱い | 理由 |
|---|---|---|---|
| S1 必ず残す | `AskUserQuestion` の質問・選択肢・回答 | 原文のまま | ユーザーの決定そのもの。最も価値が高い |
| S1 | ユーザーの発言（`type: user` で文字列 content、`isMeta` でない、スラッシュコマンドでない） | 原文のまま（1 件 2,000 字で切る） | 方針・指示・訂正・約束はここにしかない |
| S1 | コンパクション要約（`isCompactSummary`） | 原文のまま | Claude が当時の文脈で書いた一次要約。Errors and fixes / Pending Tasks が特に有用 |
| S1 | `away_summary`、`ai-title`、`last-prompt` | 原文のまま | 短くて信号が濃い |
| S1 | `is_error: true` の tool_result | 末尾 300 字だけ | 「つまずき」の検出点。直後の assistant 本文と対にして「解決」を拾う |
| S2 条件付き | assistant の `text` ブロック | ターン末尾の本文だけ残す。1 件 1,500 字で切る | 完了報告・提案・確認質問が入る。途中の「読みます」は不要 |
| S2 | `SendMessage` の入力（Agent Teams のセッション間メッセージ） | 500 字で切る。`summary` フィールドがあればそれを優先 | 統括セッションでは決定がここを通る。ただし量が多いので上限を厳しくする |
| S2 | `file-history-delta`、`pr-link`、`gitBranch` | ファイル名・PR 番号・ブランチ名だけ | 参照先（reference）の素材 |
| S2 | tool_use の `input` | ツール名と、Bash なら `description` だけ | 「何をしたか」の流れを保つための最小限 |
| S3 捨てる | tool_result の本文（Read / Bash / Grep の出力） | 捨てる | 再生成できる。全体の量の大半 |
| S3 | `thinking` ブロック | 捨てる | 途中経過。判断の結果は本文に出る |
| S3 | `attachment` 全種、`queue-operation`、`mode`、`permission-mode`、`atis-latch`、`system` の `turn_duration` / `stop_hook_summary` | 捨てる | ハーネスの内部状態 |
| S3 | `usage`、`requestId`、`apiBlockIndex` などのメタデータ | 捨てる | 課金と識別のための値 |
| S3 | `tool-results/` 配下の別ファイル | 開かない。ファイル名とサイズだけ台帳に記録 | 開くだけでメモリを食う |

### 2.3 「意思決定・方針・つまずき・約束」の見分け方

機械抽出の段で、ユーザー発言と assistant 本文に次の印を付ける。LLM 抽出はこの印を優先順位の手がかりにする。

| 種別 | 機械的な手がかり |
|---|---|
| 決定 | `AskUserQuestion` の回答。ユーザー発言に「〜で進めて」「A で」「採用」「やめる」 |
| 方針・規律 | ユーザー発言に「今後は」「常に」「必ず」「禁止」「〜しないで」 |
| 訂正（feedback） | `communication-style.md` の不満サイン語（「同じ話」「意味がわからない」「いえ、ちがう」「長い」）と「ではなく」「違う」 |
| つまずきと解決 | `is_error: true` の直後 3 ターン以内に成功した同種ツール呼び出しがある区間 |
| 約束 | ユーザー発言・assistant 本文に「あとで」「次回」「後日」「〜までに」と日付表現 |
| 参照先 | URL、Issue / PR 番号、ファイルパス、テーブル名、環境変数名 |

サブエージェントの記録（`subagents/*.jsonl`）は別扱いにする。中身の大半は探索の途中経過なので、末尾の assistant 本文（最終報告）だけを `check-jargon.py` と同じ末尾読みで取る。全文は読まない。

## 3. 圧縮パイプラインの段構成

```
 [0 台帳登録] → [1 機械抽出] → [2 LLM 抽出] → [3 統合] → [4 書き込み] → [5 検証] → [6 削除許可]
   台帳 1 行      ダイジェスト     候補事実 JSON    判定付き     memory ファイル  検証レポート   アーカイブ→削除
   (~100B)        (元の 3〜5%)     (~5〜30KB)                    + 分割索引
```

| 段 | 何をするか | 実装の性質 | モデル |
|---|---|---|---|
| 0 台帳登録 | 対象ファイルを見つけ、サイズ・mtime・プロジェクト・サブエージェント数を台帳（`~/.claude/state/compile-ledger.jsonl`）に追記。状態 `queued` | Python 標準ライブラリ。`os.scandir` と `stat` だけ | なし |
| 1 機械抽出 | 1 行ずつ読み、2 章の階層に従って残す行だけを「ダイジェスト」JSONL に書く。各行に元の `uuid` と `timestamp` を付ける。トークン数の概算を出す。状態 `digested` | 決定論的。同じ入力なら同じ出力。単体テスト可能 | なし |
| 2 LLM 抽出 | ダイジェストを読ませ、「候補事実」を JSON で出させる。コンパクション要約の区切り（`compact_boundary`）ごとに分割し、最後に統合パスを 1 回。状態 `extracted` | `claude -p` を直列で呼ぶ。出力は構造化（下のスキーマ） | 下の 3.2 |
| 3 統合 | 候補事実ごとに既存 memory から似たものを探し、「同一 / 更新 / 矛盾 / 新規」を判定。状態 `merged` | 字句一致で候補を 5 本まで絞り、LLM が判定 | 下の 3.2 |
| 4 書き込み | memory ファイルを新規作成または更新。分割索引を更新。`MEMORY.md` には索引ファイルへの 1 行だけ足す。状態 `written` | 決定論的。frontmatter の検証つき | なし |
| 5 検証 | 4 章の自動検査（根拠一致・決定再現率・索引バイト数）を通す。落ちたら `needs-review`、通れば `verified` | 決定論的 + 判定用 LLM 1 回 | 下の 3.2 |
| 6 削除許可 | 8 章の条件をすべて満たすものだけアーカイブへ移し、猶予期間後に消す。状態 `archived` → `deleted` | 決定論的 | なし |

### 3.1 候補事実のスキーマ（段 2 の出力）

```json
{
  "kind": "decision | policy | feedback | pitfall | promise | reference | status",
  "statement": "1〜3 文。主語を明示",
  "why": "背景。無ければ null",
  "how_to_apply": "次に同じ場面でどうするか",
  "evidence": [{"uuid": "元イベントの uuid", "quote": "原文からの逐語引用（40〜200 字）"}],
  "identifiers": ["#5794", "docs/foo.md", "2026-09-11"],
  "occurred_at": "ISO 8601",
  "proposed_type": "user | feedback | project | reference",
  "scope": "project | global",
  "confidence": 0.0
}
```

`quote` を必須にする理由は 4 章にある。逐語引用がダイジェスト内に部分文字列として見つからない事実は、機械的に捨てる。

### 3.2 モデルの選び方

判断が分かれる点。3 案を並べる。

| 案 | 段 2 抽出 | 段 3 判定・段 5 検証 | 概算費用（初回の 6.7GB） | 長所 | 短所 |
|---|---|---|---|---|---|
| A（推奨） | Opus 5、effort `medium` | Opus 5、effort `low` | API なら $100〜150。`claude -p` なら定額の枠を消費 | 抽出の取りこぼしと言い換えの誤りが最も少ない。後から直せない工程に強いモデルを置く | 費用が最も高い |
| B | Sonnet 5 | Opus 5 | $50〜70 | 費用半分。抽出はダイジェストの整形に近いので Sonnet でも大きく落ちない見込み | 「約束」「暗黙の方針」の拾い漏れが増える可能性。評価で確かめる必要がある |
| C | Haiku 4.5 | Sonnet 5 | $20〜30 | 最安 | 日本語の長文要約で言い換えの誤りが出やすい。「高精度」の要件と合わない |

費用の概算根拠: 段 1 で元の 3〜5% に絞ると、LLM に渡す量は全体で 15〜25M トークン程度になる見込み。ただし、これは概算にすぎない。段 1 は各セッションの概算トークン数を台帳に書くので、**LLM を 1 回も呼ぶ前に総費用が分かる**。まず段 1 だけを全件に走らせ、費用を見てから案を決めるのが順当。

呼び出し方も 2 択になる。

| 呼び出し方 | 長所 | 短所 |
|---|---|---|
| `claude -p --model <id> --output-format json`（推奨、初期） | 追加の課金設定が不要。定額の枠で動く | node プロセスが 1 本 300〜500MB 使う。**必ず直列**にし、空きメモリを見てから起動する |
| Anthropic SDK（Python）を直接呼ぶ | プロセスが軽い（数十 MB）。Batch API で半額 | API キーと課金の設定が要る。`ant auth status` で既存の資格情報を確かめてから決める |

初回の一括処理は、量が多く時間に余裕があるので、SDK の Batch API（半額、非同期）に向いている。日々の処理は `claude -p` で十分。両対応にしておき、段 2 と段 3 の呼び出し口だけを差し替えられる構造にする。

## 4. 精度の担保と検証

### 4.1 「高精度」の定義

| 指標 | 意味 | 測り方 |
|---|---|---|
| 決定再現率 | ユーザーの決定のうち、memory に残った割合 | `AskUserQuestion` の回答を正解データにする。人手ラベル不要で全セッションに適用できる |
| 根拠一致率 | 候補事実のうち、`quote` が原文に実在する割合 | 部分文字列の照合。100% 未満なら捏造の疑い |
| 識別子被覆率 | ユーザー発言に出た Issue / PR 番号・ファイルパス・数値のうち、memory か索引に現れた割合 | 正規表現で両側から抽出して比較 |
| 重複率 | 新規作成した memory のうち、既存と同一と後から判定されたもの | 段 3 の判定を別モデルで再判定して比較 |
| 後日質問の正答率 | 「このセッションで何を決めたか」型の質問に、memory だけで答えられる割合 | 下の 4.3 |
| 索引バイト数 | `MEMORY.md` が 24,576 バイト未満か | 書き込み後に測る。超えたら書き込みを差し戻す |

### 4.2 正解データの作り方

3 層で作る。

1. 自動正解: `AskUserQuestion` の回答、`away_summary`、コンパクション要約の Pending Tasks。人手不要
2. 人手ラベル: サイズと種類で層別に 10 セッション選ぶ（小 3・中 4・大 2・サブエージェント 1）。各セッションについて「残すべき事実」を 5〜15 件、ユーザーが箇条書きで書く。1 セッション 10 分程度
3. 合成データ: 決定・訂正・約束を含む 200〜500 行の小さな JSONL を手で作り、期待出力を固定する。段 1 の単体テストと、段 2 の回帰テストに使う。リポジトリに置ける

### 4.3 後日質問の試験

1. 対象セッションのダイジェスト全文を LLM に見せ、「後日、別のセッションが困りそうな問い」を 5 つ作らせる（例: 「サブメニュー 190 ページはどう扱うと決めたか」）
2. 別の LLM に、生成された memory ファイルだけを見せて答えさせる
3. 判定用 LLM が、ダイジェストを正解として採点する

問いの生成と回答を別の呼び出しにするのが要点。同じ文脈で作らせると答えが漏れる。

### 4.4 再現性

- 段 1 は決定論的。合成データで期待出力を固定し、`pytest` で回す
- 段 2〜3 は非決定的。同じ入力で 3 回走らせ、指標の範囲を報告する。しきい値は「決定再現率 95% 以上・根拠一致率 100%・索引バイト数上限内」から始める
- 評価結果は `~/.claude/state/compile-eval/<日付>/` に残し、プロンプトやモデルを変えたときに前回と比べる

## 5. 既存 memory との統合

### 5.1 重複検出

1,370 本を毎回 LLM に見せるのは無理なので、2 段にする。

| 段 | 方法 | 出力 |
|---|---|---|
| 字句で絞る | 各 memory の frontmatter（先頭 20 行）だけ読み、`name` / `description` / 本文の識別子（Issue 番号・パス・日付）を索引化する。候補事実の識別子との重なりと、description の単語一致で上位 5 本を選ぶ | 候補 5 本 |
| LLM で判定 | 候補事実と 5 本を見せ、「同一 / 更新 / 矛盾 / 新規」を 1 つ選ばせ、更新なら差分文を書かせる | 判定 + 差分 |

埋め込みベクトルによる類似検索は、外部の埋め込み API か追加ライブラリが要る。字句一致で足りるかを評価で見てから検討する。

### 5.2 判定ごとの動作

| 判定 | 動作 |
|---|---|
| 同一 | 何もしない。台帳に「既存 `<name>` と同一」と記録 |
| 更新 | 既存ファイルの本文末尾に「## 更新（YYYY-MM-DD）」節を足す。既存の文は消さない。`metadata.modified` を更新 |
| 矛盾 | 既存ファイルを触らない。候補事実を `needs-review/` に置き、ユーザーに報告する。機械で解消しない |
| 新規 | 新しいファイルを作る |

### 5.3 書式と索引

- frontmatter は現行の `metadata.type` 形式に揃える。旧形式（最上位 `type:`）は読むときに両対応する
- 圧縮由来の memory には `metadata.compiled_from: [<session_id>]` と `metadata.evidence: [<uuid>]` を足す。あとで出所を辿れる
- 既定の書き先はその transcript が属するプロジェクトの `memory/`。`scope: global` と判定された feedback だけを `-Users-h-suzuki-work/memory/` へ書く候補にし、ユーザーに確認してから移す
- 索引は 2 層にする。`MEMORY.md` には `index_compiled_<年月>.md` への 1 行だけを足し、事実ごとの行はその索引ファイルに書く。`wp-platform` で既に使われている `index_*` の運用に合わせる
- 命名は `<type>_<kebab-slug>.md`。`session-handover` スキルが書いた memory と衝突しないよう、名前が既にあれば連番を付けず「更新」判定に回す

## 6. hook 統合点

### 6.1 起動点は 4 つ

| 起動点 | 何をするか | 処理時間 |
|---|---|---|
| PreCompact hook | キューに `{session_id, transcript_path, reason: "precompact", size_at_enqueue}` を 1 行書く。それ以外はしない | 10ms 台 |
| SessionEnd hook | 同じくキューに `{reason: "session_end"}` を書く。主な入口 | 10ms 台 |
| LaunchAgent ワーカー | 10 分ごとに起動し、キューを 1 件ずつ処理する。ロックファイルで 1 本だけ動く | 1 件 1〜10 分 |
| 手動コマンド | `compile-transcripts backfill --older-than 7d` で 6.7GB の一括処理。`--dry-run` で段 1 だけ走らせ費用を見る | 数時間 |

PreCompact で同期実行しない理由: 圧縮には LLM 呼び出しが要り、30 秒の hook タイムアウトに収まらない。また、コンパクションの要約そのものが数分後に transcript へ追記されるので、その後に処理したほうが材料が揃う。PreCompact の役割は「このセッションは長い。優先度を上げて処理してほしい」と伝えることに絞る。

`{"async": true}` を 1 行目に出す非同期 hook の作法も使えるが、キューに書くだけなら同期で十分速い。非同期化はワーカー側の責務にする。

### 6.2 ワーカーの動作条件

- 起動時に `mem-guard` と同じ方法で空きメモリを見る。4GB 未満なら何もせず終わる
- 対象セッションが動いていないことを確かめる。判定は「transcript の mtime が 1 時間以上前」かつ「`~/.claude/sessions/` に生きた記録が無い」。どちらか満たさなければ後回し
- `nice -n 10` で動く。ユーザーの作業を邪魔しない
- 1 件ごとに台帳へ状態を書く。途中で落ちても次回は続きから

### 6.3 PostCompact との関係

現行の `postcompact-reinject.py` はスナップショットと `CONTEXT.md` を再注入する。第 3 段階（9 章）で、同じセッションから既に生成された memory があれば、その `name` と `description` の一覧も再注入に足す。それまでは現行のまま触らない。

## 7. 低メモリで動かすための規約

`check-jargon.py` が 109MB のログで 1,070MB を使った事故を繰り返さないための、実装者向けの決まり。

| 規約 | 内容 |
|---|---|
| 1 行ずつ読む | `for line in f:` のみ。`read()` / `readlines()` / `read_text()` を禁止する。テストで grep して落とす |
| 先に文字列で選別 | `json.loads` の前に `'"type":"user"'` などの部分文字列で候補を絞る。捨てる行は parse しない |
| 長い行は捨てる | 1MB を超える行は読まずに飛ばし、台帳に件数を記録する。実測の最大は 0.2MB |
| 書きながら進む | ダイジェストは 1 行ごとに追記する。リストに溜めない |
| 別ファイルは開かない | `tool-results/` は `stat` だけ。サブエージェントは末尾 4MB だけ読む |
| LLM は直列 | `claude -p` は同時に 1 本。次を起動する前に前のプロセス終了を待つ |
| 自己監視 | 1 件の処理ごとに `resource.getrusage` の最大 RSS を台帳に書く。300MB を超えたら処理を中断し `failed` にする |
| 計測を評価に含める | `/usr/bin/time -l` で最大 RSS を測り、100MB の入力で 150MB 未満を合格条件にする |

段 1 の出力サイズも上限を置く。1 セッションのダイジェストが 2MB を超えたら、S2 階層を落として再生成する。

## 8. 失敗時の安全性

### 8.1 台帳と状態

`~/.claude/state/compile-ledger.jsonl` に追記のみで書く。1 セッションの最新状態は最後の行。

```
queued → digested → extracted → merged → written → verified → archived → deleted
                 ↘ failed / needs-review（ここで止まる。人が見るまで進まない）
```

### 8.2 削除の条件

次をすべて満たすものだけ消す。1 つでも欠けたら消さない。

- 台帳の状態が `verified`
- ダイジェストが存在し、記録した SHA-256 と一致する
- セッションが動いていない（6.2 と同じ判定）
- transcript の mtime から 14 日以上経っている
- `--dry-run` で削除予定一覧を出し、初回はユーザーが目で見て承認している

### 8.3 2 段階の削除

1. `~/.claude/archive/transcripts/<project>/<session-id>.jsonl.xz` に圧縮して移す（Python 標準の `lzma` をストリーミングで使う。追加インストール不要。JSONL は 8〜12 分の 1 になる見込み）
2. 30 日後にアーカイブを消す

初回の一括処理では、6.7GB が 0.6〜0.8GB のアーカイブになる。これで容量の問題はほぼ解けるので、アーカイブの削除は急がなくてよい。

### 8.4 ダイジェストの恒久保存

ダイジェスト（元の 3〜5%、全体で 200〜350MB、圧縮して 40〜70MB）は消さない。役割は 3 つ。

- LLM 抽出が取りこぼしても、`grep` で原文の発言に戻れる
- memory の `evidence.uuid` から引用元を照合できる
- 将来プロンプトやモデルを変えたとき、ダイジェストから再抽出できる。元の transcript が無くても再実行できる

## 10. 判断が分かれる点のまとめ

| 論点 | 選択肢 | 推奨と理由 |
|---|---|---|
| 抽出モデル | A: Opus 5 / B: Sonnet 5 / C: Haiku 4.5 | A。取りこぼしは後から気づけない。ただし段 1 の費用見積りを見てから最終決定する |
| LLM の呼び方 | `claude -p` / SDK + Batch | 初回一括は Batch（半額・軽量）、日々は `claude -p`。両対応にする |
| 重複検出 | 字句一致 + LLM 判定 / 埋め込みベクトル | 字句一致から。追加依存を増やさず、評価で不足が出たら足す |
| 書き先 | プロジェクト memory / グローバル memory | プロジェクト既定。グローバル昇格はユーザー確認つき |
| 矛盾の扱い | 機械で上書き / 人が見る | 人が見る。memory は行動規範を含むので機械で書き換えない |
| PreCompact の役割 | 同期で圧縮 / キュー投入だけ | キュー投入だけ。タイムアウトと材料不足の両方を避ける |
| 削除 | 即削除 / アーカイブ経由 | アーカイブ経由。容量はアーカイブで 9 割減るので即削除の必要が無い |
| サブエージェント記録 | 全文処理 / 最終報告だけ | 最終報告だけ。1,797 本 2.4GB を全文処理する価値は低い |

## 11. 隠さないトレードオフ

- コンパクション要約を土台にするぶん、要約に無い細部（要約前に捨てられた小さな訂正）は落ちる。ダイジェストがユーザー発言を原文で持つので、最悪 grep で戻れる。それでも memory 化はされない
- `quote` 必須の設計は捏造を防ぐが、「複数の発言から推論した方針」のような事実を書きにくくする。推論した事実は `confidence` を下げて `needs-review` に回す運用になり、人の手間が残る
- Opus 5 を選ぶと初回に $100〜150 相当を使う。定額の `claude -p` で吸収するなら費用は見えないが、そのぶん日中の作業枠を圧迫する。夜間に回す
- `MEMORY.md` を分割索引にすると、Claude が起動時に読む索引には事実の一覧が載らない。索引ファイルを開く一手が増える。上限 24KB の制約下では避けられない
- 削除主導権を移すため `cleanupPeriodDays` を伸ばすと、ワーカーが止まっていた場合にディスク使用量が今より増える。`mem-guard` と同じ LaunchAgent でワーカーの死活も通知する必要がある
