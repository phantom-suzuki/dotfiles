# チャットメッセージ文体ガイド

ユーザー名義で送る Slack 等のチャットメッセージ（他部署・社外ステークホルダー・チーム内向け）の文体規範。実事例からの抽出で育てる。事例そのものは `~/work/workspace/message-drafts/examples/`（非公開・ローカル）を参照。

## 構成

- 1 行目で「何の件か」を宣言し、2 行目までに結論または一番のニュースを出す
- 「判明した事実」→「相手にしてほしいこと」の 2 部構成。経緯や理屈の長い前置きを書かない
- 中見出しは「■ 」（■ の後に半角スペース）、箇条書きは「・」を使う（チャットは Markdown 見出しが使えないため）
- 中項目の下をさらに分類するときは「1.」「2.」の番号、その下に「・」の二層で書く
- 保留・未確定事項を本文に散らさず、「■ 確認したいこと」に集約する
- 相手への依頼・質問は番号付きで明示し、返信すべきことを絞る
- 理由・根拠の列挙は散文にせず「・」の箇条書きにし、文末を名詞・体言で止める（「〜の制限があり、〜下がります」→「〜の制限、〜まで低下」）
- ネガティブな仮定を見出しに出さない（「うまくいかなかった場合」→「導入後のプロセス」）
- 補足は「※」始まりの 1 行にする。分類ラベルは【】で囲む

## 承認・予算依頼の型

上位者へ承認・決裁を求めるメッセージの規範。調査や分析を伴う依頼で特に効く。

- **1 文目に「背景 + 何をやめて何を入れるか + 誰と合意済みか」を圧縮し、2 文目を依頼にする。** 件名宣言と決定内容を 2 段に分けない
- 依頼は疑問形にする（「〜お願いしたいです」ではなく「〜お願いできますでしょうか？」）
- **判断の根拠にした分析過程を本文に書かない（最重要）。** 感度分析・場合分け・測定方法・実測と推定の切り分けは、こちらの検討過程であって承認者の判断材料ではない。結論の数値を 1 つ出し、幅があるときは「※〜という想定」の 1 行に畳む
- **先回りの弁明を書かない。** 想定される反論への釈明を本文へ足さず、聞かれてから答える
- 費用は【追加】【削減】の対で示す。差し引きの合計額や場合分けを並べない
- 代替案は劣る点も併記する（「代替として機能します」→「精度は落ちるが、代替手段としては機能する想定」）
- 異常に見える数字には理由を短く添える（「繁忙状態なこともあり N 件」）
- 期間は暦の区切りで書く（「4 週間」→「9 月中」）
- 締めは 1 文。承認後の段取りを書かない（「ご確認のうえご承認頂けますと幸いです。」）

## 言い回し

- 事実を淡々と、名詞ベースで書く。動作的・口語的な言い回し（「〜を仕上げて〜に見せる」）は使わない。例: 「9月中旬に開発完了したシステムを先方がレビュー」
- 中見出しも名詞句にする。語りかけ調（「〜はこう変わります」）ではなく「9月中旬に必要な成果物」のような形
- 自分の整理を相手の判断に委ねる箇所は断定しない。「〜イメージ」「〜と思われますが、いかがでしょうか？」のような仮説形で出す
- 確認事項は「〜という理解で問題ないでしょうか？」のように疑問符で終える。質問文の頭に「何の話か」の主語・文脈を補う
- 質問はできるだけ Yes/No で答えられる形に絞る
- 同じ内容を見出しと本文で繰り返さない（同義反復を削る）

## 枕詞・挨拶

- 他部署・社外宛て: 冒頭に「お疲れ様です。」を付ける
- チーム内宛て: 枕詞なし。メンション + 件名的な 1 行から入る
- 締めは、他部署・社外宛ては「よろしくお願いいたします。」、チーム内の軽い依頼は「よろしくお願いします！」

## 参照情報の書き方

- Issue/PR 等の番号だけで言及せず、「何の件か」を言葉で添える（例: 「#1132（設定移行方式の検討資料）」）
- 出典がある場合は末尾に「出典: 〜」を 1 行で添える
- 資料の URL を貼るときは、関連するものをすべて挙げ、「資料名（中身の一言説明）」+ URL の 3 点セットで並べる。1 本だけ選んで貼らない
