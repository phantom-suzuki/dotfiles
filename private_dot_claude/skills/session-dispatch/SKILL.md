# Session Dispatch Skill

1 つのアクションプランを、**人間が別々に立ち上げる複数の Claude Code セッション**へ分割して配る。配り方の実体は「memory に共通ルール＋担当表を 1 本置き、全枠共通の起動プロンプトを渡す」ことである。

## まず判定する: セッション分割か、セッション内の並列か

この 2 つは似ているが仕組みが違う。取り違えると、片方の前提（同一プロセス内でメッセージを送り合える／送り合えない）が崩れる。

| | セッション分割（本スキル） | セッション内の並列（`parallel-work-decision`） |
|---|---|---|
| 実体 | 人間が別ウィンドウ・別プロセスで Claude Code を複数立ち上げる | 1 つのセッションが Agent を複数動かす |
| 連絡手段 | **無い。** GitHub（Issue / PR）と memory を介してのみ伝わる | `SendMessage` で直接やり取りできる |
| 向く規模 | 1 枠が数時間〜数日。人間が枠ごとに会話したい | 1 枠が数十分。司令塔が結果をまとめる |
| 中断への強さ | 強い（各セッションが独立して畳める） | 弱い（親が落ちると全体が落ちる） |
| 人間の関与 | 枠ごとに判断を仰げる | 司令塔経由で 1 本化される |

**判断の目安**: 各枠で**ユーザーの判断を個別に仰ぐ必要がある**なら分割。機械的に処理して結果だけ集めたいなら `parallel-work-decision`。両方混ぜてもよい（各セッションが内部で Agent を並列に使う）。

## 分割の切り方

1 枠 = **1 セッションで完結し、他の枠の完了を待たずに着手できるまとまり**。次の 3 点で切る。

- **触るファイルが重ならない**。同じファイルを 2 枠に割り当てると、後から入れる側が必ず衝突の解消をやる。重なるなら 1 枠にまとめるか、順番待ちにする
- **依存の向きが一方向**。相互に待ち合う 2 枠を作らない。片方が待つなら「何を待つか」を待つ側の行に書く
- **粒度が揃っている**。1 枠が他の 5 倍重いと、その枠だけ終わらず全体が止まる。重い枠は先に分割する

依存で待つ枠は、**待っている間にできる下調べ**を行に書いておくと遊ばない。

## 手順

### Step 1: 振り分け memory を書く

保存先は memory ディレクトリ。

```bash
PROJECT_KEY=$(pwd | sed 's|/|-|g')
MEMORY_DIR="$HOME/.claude/projects/${PROJECT_KEY}/memory"
```

`MEMORY_DIR` は既に在る前提で直接書く。ファイル名は `project_<何の振り分けか>_dispatch.md`。

```markdown
---
name: project_<scope>_dispatch
description: <何の>並列セッション振り分け表（<枠の一覧>）。起動プロンプトは「memory の project_<scope>_dispatch を読み、担当 <枠> を進めてください」。共通ルール = <最重要のルール 2 つ>
metadata:
  type: project
---

<1〜2 文で背景。いつ・誰の指示でこの体制にしたか。>

起動プロンプトは **「memory の project_<scope>_dispatch を読み、担当 <枠> を進めてください」**。

## 共通ルール（全セッション）

<ここが最重要。> 各セッションは互いに見えないので、衝突と品質のばらつきはルールでしか防げない。

- **完了の条件**（何を満たせば「done」か。レビュー・CI・テストの基準）
- **各枠が自分で決めてよい範囲と、ユーザーに伺う範囲の線引き**
- **共有資源の触り方**（マージの順序・共有ファイル・共有環境。直列化が必要なら明記）
- **ブロックしたときの振る舞い**（他セッションが拾える形で Issue / PR にコメントを残して次へ）
- **記録の残し方**（自分の行だけ更新する・他の枠の記述は消さない）

## 担当表（<日付>時点）

| 枠 | 担当 | 内容・現在地 |
|---|---|---|
| <枠> | <対象> | <何をするか（言葉で）。前提・落とし穴・すでに分かっている事実・依存の待ち> |

## プール（優先度後ろ・枠が空いたら）

- <どの枠にも入らない残りタスク>

## 関連

[[関連 memory]]
```

### Step 2: 各行に「現在地」を書く

行は指示書ではなく**引き継ぎ文書**として書く。着手するセッションは前提を知らない。少なくとも次を入れる。

- **何をするか**を言葉で（番号だけにしない。「#1108 を進めて」ではなく「フォーム送信の POST が CloudFront を通る経路を作る（#1108）」）
- **すでに分かっている事実**と出典（同じ調査を繰り返させない）
- **落とし穴**（先に踏んだ罠。踏み直させない）
- **依存の待ち**（何を待つか・待っている間にできること）
- 進行中なら **worktree のパスとブランチ**

### Step 3: 起動プロンプトを提示する

全枠で**同一の 1 行**にし、担当名だけ差し替える形にする。枠ごとに文言を変えると、ユーザーが枠の数だけ別の文を管理することになる。

```
memory の project_<scope>_dispatch を読み、担当 <枠> を進めてください
```

提示のときは、枠と内容の対応表を添える（ユーザーがどのウィンドウで何を立ち上げるか分かる形）。

| 枠 | 起動プロンプト | 内容 |
|---|---|---|
| R-1 | `memory の … 担当 R-1 を進めてください` | <言葉で 1 行> |

### Step 4: 各セッションの更新運用を決めて書く

振り分け表は**全セッションが同じファイルを編集する**。壊さないための決めごとを memory 本文に書く。

- 自分の枠の行だけ更新する。他の枠の行は読むだけ
- 行が長くなったら、詳細は別の引き継ぎ memory（`session-handover` スキル）へ出し、行からリンクする
- 完了したら行を消さず「完了」と結果を残す。消すと、後から来たセッションが同じことを再検討する
- 編集前に必ず読み直す（他セッションが先に書き換えている）

## 落とし穴

| 落とし穴 | 何が起きるか | 防ぎ方 |
|---|---|---|
| 枠名を番号だけにする | どのウィンドウが何の担当か分からなくなる | 表で枠と内容を対応させ、行にも言葉で書く |
| 同じファイルを 2 枠に割り当てる | 後から入れる側が毎回衝突を解消する | 切るときにファイル単位で重なりを確認する |
| 共通ルールを書かない | 枠ごとに完了基準がばらつき、品質が揃わない | 完了条件と伺いの線引きを最初に固定する |
| 直列化が必要な資源を書かない | 同時に触って壊す・待ちが発生して混乱する | マージ順・共有環境の触り方を明記する |
| 依存を「あとで」で済ませる | 待つ側が何を待つか分からず止まる | 待つ対象と、待つ間にできることを行に書く |
| 完了した行を消す | 後続セッションが再検討を始める | 「完了」と結果を残す |
| プランだけ渡して事実を渡さない | 各セッションが同じ調査を繰り返す | 分かっている事実と出典を行に入れる |

## 関連

- `parallel-work-decision` — 同一セッション内で Agent を並列に動かす場合の判定
- `session-handover` — 1 枠の到達点を次セッションへ引き継ぐ（行が長くなったらこちらへ出す）
- `~/.claude/rules/communication-style.md` — 番号だけで人間に言及しない規範（枠名・行の書き方に効く）
