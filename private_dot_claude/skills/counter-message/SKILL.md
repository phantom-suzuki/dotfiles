# Counter Message Skill

通常のコミュニケーションでは使わない。理不尽な要求・事実と違う非難・一方的な指示を、黙って受け入れると同じことが繰り返されるときに、感情ではなく事実と論理で異議を述べ、認識と依頼の形の修正を求めるメッセージを作る。

文体の規範は `message-draft` スキルのもの（`~/.claude/skills/message-draft/references/style-guide.md`）を読んで継承する。本スキルが持つのは、証拠の集め方・整理の形・擦り合わせの順・反論の型・点検表である。

## データ配置

| 層 | パス | 管理 | 内容 |
|---|---|---|---|
| 手順と型 | 本ディレクトリ | dotfiles（public） | 一般化した手順・矛盾の型・反論の型。固有名詞・社内情報を含めない |
| 事例 | `~/work/workspace/message-drafts/examples/` | ローカル（非公開） | 実メッセージの全文と抽出した規範。`message-draft` と共用 |

## 原則

- **送信・投稿はスキルが行わない。** 文案はユーザーが全文を確認し、ユーザーが送る。Codex 経由で送るのは、ユーザーがそう指示したときだけ
- **事実は原文で裏取りする。** 要約や記憶で書かない。日時・投稿者・ts・permalink を揃える
- **自分側の弱みを決めつけない。** 弱みに見える事実は「候補」としてユーザーに確かめる。ユーザーにとっては論点の入口であることが多い
- **相手の動機を書かない。** 構造（何を相手側が自分で決め、何を自分側に求めたか）を示す
- **補った細部は承認を得てから成果物に入れる。** お願いの中身・打ち合わせの提案・運用の条件は、ユーザーが選んだものだけを書く

## 実行手順

### Step 1: 状況の把握

ユーザーから次を聞く（すでに語られていれば聞き直さない）。

- 相手の文面（リンクか全文）と、何に納得していないか
- 望む着地: 関係を正す / 要求を退ける / 記録を残す / 相手に認識の修正を求める
- 送り先: スレッドか DM か、同席者は誰か、いつ送るか
- 決着済みの事柄（今日の対応など）。決着済みなら文面で「進め方の話ではない」と切り分ける

### Step 2: 証拠の収集

[references/evidence-collection.md](references/evidence-collection.md) の雛形で Codex に読み取り専用の調査を依頼する。並行して手元の記録（決定記録・docs・memory）を引く。

集めるもの: 取り決めの初出と全文 / 依頼の初出・追加・変更の時刻 / 自分側の対応の時刻 / 相手の引用と原文の差 / 同じ型の前例。

### Step 3: 整理 Artifact

[references/evidence-collection.md](references/evidence-collection.md) の章立てで Artifact を作る。チャットには結論 1〜3 行とリンクだけを書く。

章: 要点 / 送る文面（全文。文案ができたら要点の直下に置く）/ 時系列 / 合意事項の全文（相手の引用の欠けを印で示す）/ ユーザーの主張ごとの証拠の強さ / 自分側の弱みの候補 / 一般論（任意）。

### Step 4: 擦り合わせ①（弱み・観点・着地）

`AskUserQuestion` で順に確かめる。

1. 弱みの候補は本当に弱みか。ユーザーの答えで Artifact を直す
2. 観点 3〜4 つ（[references/argument-patterns.md](references/argument-patterns.md) の矛盾の型から選ぶ）
3. 着地の 1 文（例: 「対等な協働関係であり、依頼は一方的な指示ではなく相談として扱う」）

逐条（相手の文を 1 文ずつ引用して反論）は使わない。観点で束ねる。

### Step 5: 擦り合わせ②（お願い）

お願いの候補を `multiSelect` で出し、選ばれたものだけを書く。入れないもの: 運用の条件（「〜の場合は翌営業日」）、打ち合わせの提案、相手の動機への言及。求める姿勢は「認識してほしい」の水準で書く。

### Step 6: 文案

[references/message-rules.md](references/message-rules.md) の型で書く。全文を Artifact にも載せ、ユーザーは節ごとに直す。全文を一度に確定しようとせず、節ごとに合意を積む。

### Step 7: 点検と送信後

[references/message-rules.md](references/message-rules.md) のセルフチェック表を当ててから最終版を出す。送信はユーザー。最終版を受け取ったら:

1. 事例を `~/work/workspace/message-drafts/examples/YYYY-MM-DD-<slug>.md` に保存（状況 / 版の変遷と差し戻しの理由 / 最終版 / 抽出した規範）
2. 一般化できる規範は `references/message-rules.md` へ匿名化して昇格し、chezmoi のソースを直して apply する

## エラーハンドリング

| 事象 | 対応 |
|---|---|
| Codex が Slack を読めない | `~/.claude/rules/codex-monitoring.md` の手順で 1 回やり直す。だめなら原文のリンクをユーザーに頼まず、取れた範囲と取れなかった範囲を Artifact に明記する |
| 相手の発言がスレッド外（会議・口頭） | 原文が無いことを明記し、構造の指摘としてだけ書く。引用はしない |
| ユーザーが「弱い」と言う | 事実の量を増やすのではなく、観点の切り方を変える（[references/argument-patterns.md](references/argument-patterns.md)） |
| ユーザーが「法的・証拠を突きつける感じ」と言う | 逐条をやめ、観点 3〜4 つに束ね直す |
