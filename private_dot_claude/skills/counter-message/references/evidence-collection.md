# 証拠の収集と整理 Artifact

`counter-message` の Step 2〜3 の詳細。固有名詞は書かない。

## 1. Codex への依頼の雛形

読み取り専用。投稿・リアクション・ファイル変更は禁止。`--model` と `--effort` を明示する（検索範囲が広いので `high` を基本にする）。

```
## 目的
<チャンネル ID>/<permalink> の <相手> の投稿（ts=…）に返答するための事実を集める。

## 調べること（各項目に 投稿者・JST 日時・ts・permalink・原文の引用 を付ける。要約しない）
1. 対象の投稿の原文全文と、同じスレッドの前後の投稿
2. 相手が引用・言及している取り決めやルールの、初出の投稿と全文。誰が書き、誰が了承したか
3. 今回の依頼・要求の初出、素材が揃った時点、追加・変更の時刻
4. 自側の対応の時刻（反映・返答・申し出）
5. 同じ型の前例（過去に同じ条件でどう扱ったか）
6. 「〜というルールがある」と相手が言うものの明文の有無。無ければ「見つからなかった」と、検索した語と範囲を書く

## 出力
Markdown。項目ごとに時系列の表（JST / 投稿者 / 要旨 / 原文引用 / permalink）。
末尾に「見つからなかったもの」「検索した語・チャンネル・期間」。推測は推測と明記する。
```

初回の結果を読んだら、鍵になる投稿の**全文**を追加で取る（1 回目は要旨になりがち）。全文が無いと、相手の引用の欠けを示せない。

## 2. 手元の記録

- 決定記録・引き継ぎ memory・docs の手順書に、取り決めの経緯や自側の判断が残っていることが多い。Slack と突き合わせる
- 時刻は `date` で JST に直す（Slack の ts は UNIX 秒）

## 3. 整理 Artifact の章立て

HTML の Artifact。ライト / ダークの切り替えボタンを付ける（`rules/artifact-conventions.md`）。チャットには結論 1〜3 行とリンクだけ。

| 章 | 中身 | 注意 |
|---|---|---|
| 要点 | 4〜6 行。決着済みの事柄、相手の引用の欠け、自側が満たしている条項、使える論点、弱みの候補 | 最初の版では「見立て」と明記する |
| 送る文面（全文） | 文案ができたら要点の直下に置く。版と送信予定を添える | ユーザーは「結論としてどこを見ればよいか」を最初に探す |
| 時系列 | JST / 投稿者 / 内容 / 原文リンク。鍵の行に印。自側と相手側を色で分ける | 自側の対応の時刻（条項を満たした時刻・修正にかかった時間）を必ず入れる |
| 合意事項の全文 | 相手が引いた部分と、引かなかった部分を印で示す | 「翌日に延期」「個別に調整」のような例外条項が落ちていることが多い |
| ルールの当てはめ | 取り決めの数え方（営業日など）を表にし、どの依頼が内外かを示す | 自側が「受けた」事実があれば「違反」とは書かない。「相手側が満たしていない条項を、自側が前倒しで受けた」と書く |
| 主張と証拠の強さ | ユーザーの主張ごとに 強い / 弱い と理由 | 弱い主張をそのまま送ると反論される。先に伝える |
| 使える論点と弱みの候補 | 弱みは「候補」。ユーザーに確かめるまで断定しない | 作業者の予定・1 回目の差分・余裕の無さは、ユーザーには弱みでないことがある |
| 一般論 | 業界の慣行・公開されている運用例。本文には入れないことが多い | 「申請期限と期限外の扱いを事前に決める」を支える程度 |
| 方針 | ユーザーの決定を時刻付きで記録 | 後から読み返す人のため |

## 4. 弱みの候補の確かめ方

弱みに見える事実は、次の形でユーザーに確かめる。

- 「〜と書いています。相手はここを突いてくる可能性があります。どう扱いますか」
- 選択肢: 触れない / 先に事情を説明する / 論点を変えて答える（例: 作業者の予定は自側の段取り。相手に必要なのは公開の時刻と確認の体制だけ）

ユーザーが「問題ない」と言ったら、Artifact の弱みから外し、論点の入口（「当日中が必須なら事前に体制を相談すべき」など）に置き直す。
