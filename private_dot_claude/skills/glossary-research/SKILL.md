# Skill: glossary-research

## 概要

Claude が日本語で書くときに使う用語集（`~/.claude/docs/glossary/`）を育てる。
用語集が不足すると、Claude は標準語を思い出せずに和語の造語を作る。2026-09-19 の実測では、
`AskUserQuestion` 2,065 件に「写し」「飛ばし」「名乗り」「横送り」などの造語が混ざっていた。

用語集には 2 つの層がある。

| 層 | 置き場所 | 中身 |
|---|---|---|
| 共通 | `~/.claude/docs/glossary/` | 分野をまたぐ用語（設計 / インフラ / 開発プロセス / セッション運用）と内輪語の対応表 |
| プロジェクト | 作業中リポジトリの `docs/glossary/` | その業界と業務の用語（WordPress のサイト移行、婚活サービスの業務、名刺管理 など） |

## 使う場面

| 引数 | 場面 | 出口 |
|---|---|---|
| `research` | 新しいプロジェクトに入った。業界用語を知らない | プロジェクト側の `docs/glossary/<分野>.md` |
| `review` | 週 1 回の造語候補を判定する | `~/.claude/docs/glossary/jargon.md` |
| `add <語>` | ユーザーに「その言葉がわからない」と言われた | `~/.claude/docs/glossary/jargon.md` |

引数が無いときは、`~/.claude/state/glossary-candidates.md` が 7 日以内に更新されていれば `review`、
そうでなければ何をするかをユーザーに聞く。

## 安全原則

- **用語集を自動で書き換えない。** 足す行を提示し、ユーザーが承認した行だけ反映する
- **編集は chezmoi ソース側**（`~/.local/share/chezmoi/private_dot_claude/docs/glossary/`）に行う。
  反映は `chezmoi apply`。プロジェクト側の用語集はそのリポジトリで直接編集する
- **`glossary-candidates.md` を dotfiles に入れない。** 会話の断片を含む。実機のローカルに置いたままにする
- **検出パターンは誤検知しない形にする。** 一般語と衝突するなら `—` にして辞書としてだけ使う
- Web リサーチは Codex へ委譲する（`task-delegation` スキル）。モデルと effort を毎回明示する

## research: 新しいプロジェクトの業界用語を集める

### Step 1: 分野を決める

リポジトリから読み取る。`README.md`・`CLAUDE.md`・`docs/`・主要なディレクトリ名・
`package.json` や `go.mod` の依存を見て、次の 2 つを書き出す。

- **技術の分野**: 使っている基盤と道具（WordPress / Terraform / Go / React など）
- **業務の分野**: 何の事業か（結婚相談所の集客サイト / 名刺管理 / 音声の文字起こし など）

業務の分野は、コードだけからは読み取れないことがある。読み取れなければユーザーに 1 問だけ聞く。

### Step 2: 用語を集める

技術の分野は一次情報（公式ドキュメント）から、業務の分野は業界団体・業界誌・
公的機関の資料から集める。個人ブログと生成 AI の要約は出典にしない。

Codex へ委譲する。1 分野ごとに 1 回、次の形で依頼する。

```
<分野> の日本語の標準用語を 40〜60 語集めてください。条件:
- 出典は公式ドキュメント・業界団体・公的機関の資料に限る。URL を語ごとに添える
- 日本語の定訳が無い語は、英語のまま使うべきか片仮名にすべきかを書く
- 現場で使われているが誤用されがちな語は、正しい用法と誤用を分けて書く
- 出力は Markdown の 4 列の表: 用語 / 意味（1 文） / 初出で添える説明（1 句） / 注意
```

モデルと effort は `research` の性質（Web を読んで広く集める）から `gpt-5.6-terra` / `high` を使う。
判断を誤ると用語集ごと誤りが入るので、`medium` には下げない。

### Step 3: 突き合わせて重複を落とす

共通の用語集（`~/.claude/docs/glossary/` の 4 ファイル）に既にある語は、プロジェクト側に入れない。
表の見出し列だけを読んで照合する。

```bash
grep -h '^| ' ~/.claude/docs/glossary/{design,infra,process,ai-agent-ops}.md \
  | sed 's/^| *//; s/ *|.*//' | sort -u > /tmp/known-terms.txt
```

### Step 4: 提示して承認を得る

分野ごとに語数と、その分野で特に間違えやすい語を 3 つ挙げて示す。
全文をターミナルに書き出さない。ユーザーが承認したら書き込む。

### Step 5: 書き込む

プロジェクトの `docs/glossary/<分野>.md` に 4 列の表で書く。書式は
`~/.claude/docs/glossary/README.md` の「エントリの書式」に従う。
そのリポジトリの `CLAUDE.md` に「日本語で書くときは `docs/glossary/` を引く」と 1 行足す。

Markdown を新規作成したので、完成報告の前に `doc-polish` スキルで表現を研磨する。

## review: 週 1 回の造語候補を判定する

`~/.claude/state/glossary-candidates.md` を読む。無ければ作る。

```bash
~/.local/bin/glossary-candidates --days 7
```

このファイルには 2 つの表がある。

**既知の内輪語の再発。** `jargon.md` に載せたのに使われ続けている語。
件数が前週より減っていない語は、`jargon.md` の補足に `[block]` を足して
応答を差し戻す設定に上げることを検討する。上げる条件は次の 2 つを満たすこと。

- 検出パターンが一般語と衝突しない（用例を 10 件読んで誤検知が 0 件）
- 2 週続けて件数が減っていない

**新しい造語の候補。** IT の文脈に出た和語の名詞。1 語ずつ次の 3 つに分ける。

| 判定 | 例 | 反映先 |
|---|---|---|
| 造語。標準用語がある | 帯 → バナー、絵 → 画像、見張り → 監視 | `jargon.md` の表に 1 行足す |
| 普通の日本語 | 準備 / 記事 / 画面 | `glossary-candidates` の STOPWORDS に足す |
| 判断がつかない | 区画 / 台本 | 何もしない。次週また出たら判断する |

判定に迷ったら、その語で検索して IT の記事が出るかを見る。出なければ造語である。

判定の結果を表で提示し、承認された行だけ反映する。反映は chezmoi ソース側に行い、
`chezmoi apply` で実機へ渡す。

## add: 指摘されたその場で足す

ユーザーが「その言葉がわからない」と言ったときの手順。会話を止めないよう、3 つを続けて行う。

1. その場で標準語に言い換えて答え直す
2. `jargon.md` の適切な節に 1 行足す。検出パターンは誤検知しない形にする
3. 置き換え先の標準語が分野別ファイルに無ければ、そちらにも足す

その語をユーザーが指摘した日付を補足の列に書く。あとで判断の根拠になる。
