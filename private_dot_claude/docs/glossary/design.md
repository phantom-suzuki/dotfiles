# ソフトウェア設計・アーキテクチャ・実装品質の用語

設計の話は抽象度が高く、Claude がその場しのぎの日本語の比喩を作りやすい。
層の名前・DDD の用語・テストダブルの分類は原典に定義があるので、そちらを使う。
「ユーザーへの言い方」の列は、専門用語をいっさい使わずに要点だけを伝える言い方を置く。

## アーキテクチャの型

| 用語 | 意味 | ユーザーへの言い方 | 注意 |
|---|---|---|---|
| レイヤードアーキテクチャ | 責務ごとに層を積み、上の層だけが下の層を呼ぶ構造 | 役割ごとに分けて積み、呼ぶ向きを一方向にそろえる | 「3 層アーキテクチャ」は層が 3 つの具体例 |
| Clean Architecture | 依存の向きを内側だけに限定した同心円の層構造 | 業務のルールを中心に置き、外側の技術に依存させない | 層名は原典の 4 つを使う（下の 4 行） |
| Entities（エンティティ層） | Clean Architecture の最内層で、企業全体の業務ルールを持つ | どの画面でも変わらない、業務そのもののルール | DDD のエンティティとは別物なので混同しない |
| Use Cases（ユースケース層） | アプリ固有の処理手順を組み立てる層 | このアプリで何ができるかを決める手順の置き場 | 「アプリケーション層」「インタラクタ」とも呼ばれる |
| Interface Adapters（インターフェースアダプタ層） | 外側の形式と内側の形式を変換する層 | 外とやり取りする形に、データを詰め替える場所 | Controller / Presenter / Gateway がここに入る |
| Frameworks and Drivers（フレームワーク・ドライバ層） | DB・Web フレームワーク・外部サービスなど具体技術の層 | 差し替えられる道具そのものを置く、いちばん外側 | 「インフラ層」と呼ぶ流儀もあるが原典はこの名前 |
| 依存性のルール（Dependency Rule） | ソースコードの依存は外側から内側へ一方向にしか向かわない規則 | 呼んでよい向きを内向きだけに固定する決まり | Clean Architecture の中核。実行時の呼び出し方向とは別 |
| ヘキサゴナルアーキテクチャ | アプリ本体を中心に置き、外部との接点をすべて差し替え可能にする構造 | 本体は変えずに、外とのつなぎだけ取り替えられるようにする | 別名 Ports and Adapters。Cockburn の原典名を使う |
| ポート（Port） | アプリ本体が外部とやり取りするために定義する呼び出し口 | 本体が「こう呼んでほしい」と決めた呼び出し方の形 | 実装ではなく定義。Go なら interface が対応する |
| アダプタ（Adapter） | ポートの形と実際の技術を変換する実装 | 決めた呼び出し方に、実物の技術を合わせる部品 | GoF の Adapter パターンと名前が同じだが粒度が違う |
| 駆動側アダプタ（Primary / Driving） | アプリを外から呼び出す側のアダプタ | アプリに仕事を頼む側のつなぎ | HTTP ハンドラや CLI がこれにあたる |
| 被駆動側アダプタ（Secondary / Driven） | アプリが外へ問い合わせる側のアダプタ | アプリが頼る側のつなぎ | DB クライアントや外部 API クライアントがこれ |
| モノリス | 1 つの配置単位にすべての機能を収めた構成 | 全部を 1 つにまとめて動かすやり方 | 「悪い構成」の意味ではない。規模次第で最適解 |
| モジュラーモノリス | 1 つの配置単位のまま、内部を強い境界で分割した構成 | まとめて動かすが、中の区切りははっきり分ける | マイクロサービス化の前段として選ばれることが多い |
| マイクロサービス | 業務単位で分けた小さなサービスを独立に配置・運用する構成 | 機能ごとに別々のプログラムに分け、別々に更新する | 組織の分割と合っていないと運用コストだけ増える |
| 分散モノリス | 分割されているのに一斉に配置し直さないと動かない状態 | 分けたはずなのに、結局まとめて出すしかない状態 | マイクロサービス化の典型的な失敗。批判語として使う |
| イベント駆動アーキテクチャ | 起きた出来事を通知として流し、受け手が自律的に反応する構成 | 「起きたこと」を知らせて、受けた側が勝手に動く作り | 呼び出し順が見えにくくなるので追跡の仕組みが要る |
| CQRS | 更新用のモデルと参照用のモデルを分離する設計 | 書き込み用と読み取り用でデータの持ち方を分ける | Fowler は「複雑さが増す」と警告。適用は狭い範囲に限る |
| イベントソーシング | 状態そのものではなく、状態を変えた出来事の列を正本として保存する方式 | 今の値ではなく、変化の記録をすべて残して積み上げる | CQRS とセットで語られるが独立した選択肢 |
| Saga パターン | 複数サービスにまたがる処理を、補償操作つきの一連の局所処理で実現する方式 | 途中で失敗したら打ち消す手順を用意して、分けて進める | 全体を 1 つのトランザクションにできない場面で使う |
| パブリッシュ / サブスクライブ | 送り手が宛先を知らずに発信し、受け手が購読して受け取る通信方式 | 宛先を決めずに流し、欲しい人が受け取る | 1 対 1 のキュー消費とは別の形 |
| BFF（Backend for Frontend） | 画面ごとの都合に合わせた API をその画面専用に用意する層 | 画面ごとに、そこで使いやすい形の API を別に置く | 画面が増えると数も増えるので維持コストを見積もる |
| ストラングラーフィグ | 旧システムを止めずに、機能単位で新実装へ置き換えていく移行方式 | 古い仕組みを動かしたまま、少しずつ新しい方へ寄せる | 一括置き換え（ビッグバン移行）の対義として使う |

## 設計原則

| 用語 | 意味 | ユーザーへの言い方 | 注意 |
|---|---|---|---|
| 単一責任の原則（SRP） | 1 つのモジュールが変更される理由は 1 つだけであるべきという原則 | 直す理由が 2 つ以上あるなら、分けたほうがよい | 「1 つのことだけをする」は誤読。判断軸は変更を依頼する人 |
| 開放閉鎖の原則（OCP） | 拡張には開き、修正には閉じているべきという原則 | 機能を足すときに既存を書き換えなくて済む形にする | 将来の拡張点を先読みしすぎると YAGNI に反する |
| リスコフの置換原則（LSP） | 派生型は基底型と入れ替えても呼び出し側が壊れてはいけないという原則 | 差し替えても、呼ぶ側が書き換えずに済むようにする | 実装の継承より interface の契約として考えると使いやすい |
| インターフェース分離の原則（ISP） | 利用側が使わないメソッドへの依存を強制されてはいけないという原則 | 使わない機能まで持たされる形にしない | Go では小さい interface を呼び出し側で定義する形が対応 |
| 依存性逆転の原則（DIP） | 上位モジュールも下位モジュールも抽象に依存すべきという原則 | 中身の実装ではなく、約束した形のほうに合わせる | 依存性注入（DI）は実現手段の 1 つで、同じ語ではない |
| DRY | 同じ知識の表現をシステム内で 1 か所に保つ原則 | 同じ決まりごとを 2 か所に書かない | 「似たコード」ではなく「同じ知識」が対象。早すぎる共通化に注意 |
| YAGNI | 今必要でない機能は作らないという原則 | 今いらないものは作らない | 拡張性の議論を打ち切る根拠として使える |
| 関心の分離 | 異なる目的のロジックを別々の場所に置く設計方針 | 目的が違う処理を、同じ場所に混ぜない | 層分割・モジュール分割の共通の根拠 |
| 結合度（Coupling） | モジュール同士がどれだけ互いの内部に依存しているかの度合い | 片方を直すと、もう片方も直す必要が出る度合い | 低いほどよい。日本語と英語のどちらでも通じる |
| 凝集度（Cohesion） | 1 つのモジュール内の要素がどれだけ同じ目的に向いているかの度合い | 1 か所に集めた中身が、同じ目的でそろっている度合い | 高いほどよい。結合度と逆向きなので言い間違えに注意 |
| 依存性注入（DI） | 依存する実装を内部で作らず外から渡す手法 | 使う相手を自分で作らず、外から受け取る | DI コンテナは実現の道具であって原則ではない |
| 制御の反転（IoC） | 処理の呼び出し順の決定権をフレームワーク側へ渡す設計 | 呼ぶ順番を自分で決めず、土台となる仕組みに任せる | DI は IoC の一形態。上位語として使う |
| カプセル化 | 内部状態を隠し、決められた操作経由でのみ変更させること | 中身を直接いじらせず、決めた操作だけを公開する | getter / setter を全部生やすと実質的に破れている |
| 抽象化の漏れ | 隠したはずの下位の詳細が、利用側に影響を及ぼす状態 | 隠したはずの中身の事情が、使う側に漏れて出てくる | 英語は Leaky Abstraction。ORM や ネットワーク層でよく起きる |
| 循環依存 | 2 つ以上のモジュールが互いを参照し合う状態 | 互いに相手を呼び合っていて、切り離せない状態 | 層の境界違反として検出できる。Go では package 循環が compile error |
| 継承より合成 | 振る舞いの再利用は継承ではなく部品の組み合わせで行う指針 | 機能を引き継ぐより、部品として持たせる | Go には継承がなく、埋め込みと interface でこれを実現する |
| 早すぎる最適化 | 計測せずに性能目的でコードを複雑化すること | 測る前から速さのために作りを込み入らせること | 批判語。まず計測すべきという主張とセットで使う |

## ドメイン駆動設計（DDD）

| 用語 | 意味 | ユーザーへの言い方 | 注意 |
|---|---|---|---|
| ドメイン | ソフトウェアが対象とする業務の領域そのもの | そのソフトが扱う仕事の範囲 | インターネットのドメイン名とは無関係 |
| サブドメイン | ドメインを業務上の意味で分割した部分領域 | 仕事の範囲を、意味のまとまりで分けた一区画 | 中核・支援・汎用の 3 種に分類する |
| ユビキタス言語 | 開発者と業務の専門家が同じ意味で使う、モデルに直結した共通の語彙 | 関係者全員が同じ意味で使う、決めた言葉づかい | 「共通言語」と訳さずカタカナで統一する |
| 境界づけられたコンテキスト | 1 つのモデルとその語彙が一貫して通用する範囲 | 同じ言葉が同じ意味で通じる、はっきりした区切り | 送り仮名は「境界づけられた」に統一する |
| コンテキストマップ | 複数の境界づけられたコンテキスト間の関係を書き表した図 | 区切りどうしが、どうつながっているかの見取り図 | 図そのものより、関係の種類を決める議論が本体 |
| エンティティ | 属性が変わっても識別子で同一と判断される対象 | 中身が変わっても、同じものだと見分けられるデータ | Clean Architecture の Entities 層とは別概念 |
| 値オブジェクト | 識別子を持たず、値がすべて等しければ同一とみなす対象 | 中身が同じなら同じものとして扱う、小さなデータ | 不変にするのが原則。金額・期間・住所が典型 |
| 集約（Aggregate） | 1 つの単位として扱うドメインオブジェクトのまとまり | まとめて 1 つとして保存・更新する、データのかたまり | Fowler の定義では、トランザクションは集約の境界を越えない |
| 集約ルート | 集約の外から参照してよい唯一の入口となるオブジェクト | そのかたまりに触るときの、ただ 1 つの入口 | 外から中の要素を直接持ち出さない |
| 不変条件（Invariant） | 常に成り立っていなければならない業務上の条件 | いつでも必ず守られていなければいけない決まり | 集約の境界を決める主な根拠になる |
| リポジトリパターン | 集約の保存と取り出しを、コレクションのように見せる抽象 | 保存先を隠して、置き場から出し入れするように見せる | Git のリポジトリと紛れるので必ず「パターン」を付ける |
| ファクトリ | 生成手順が複雑なオブジェクトの組み立てを引き受ける仕組み | 作り方が込み入ったものを、まとめて組み立てる係 | 組み立て時に不変条件を満たすのが役目 |
| ドメインサービス | 特定のエンティティにも値オブジェクトにも属さない業務ロジック | どのデータの持ち物とも言えない業務の処理 | 増やしすぎると貧血ドメインモデルになる |
| アプリケーションサービス | ユースケースの手順を組み立て、ドメインを呼び出す薄い層 | 業務の処理を呼ぶ順番だけを書く、薄い取りまとめ役 | 業務ルールを書き始めたら層を間違えている |
| ドメインイベント | 業務上意味のある出来事を、過去形で表した記録 | 「何が起きたか」を業務の言葉で残した記録 | 名前は過去形にする（例: 注文が確定した） |
| 腐敗防止層（ACL） | 外部モデルを自分のモデルへ翻訳し、汚染を防ぐ変換層 | 外から来た形を、自分たちの言葉に翻訳して受け取る | Anticorruption Layer の訳。「汚染防止層」とは書かない |
| 貧血ドメインモデル | 業務ロジックを持たず、値の入れ物にとどまるモデル | データを入れるだけで、判断を何もしない作り | 批判語。Fowler の定義では「costs はあるが benefits がない」 |

## API・インターフェース設計

| 用語 | 意味 | ユーザーへの言い方 | 注意 |
|---|---|---|---|
| REST | 資源を URL で表し、統一された操作方法でやり取りする設計様式 | 扱う対象に住所をつけて、決まったやり方で読み書きする | Fielding の定義では制約の集合。JSON を返せば REST ではない |
| リソース | REST で URL によって識別される対象 | 読み書きの相手になる 1 つ 1 つの対象 | 動詞ではなく名詞で表す |
| ステートレス | サーバが要求間の文脈を保持しない性質 | 1 回ごとの依頼だけで判断でき、前回を覚えていない | REST の必須制約。台数を増やしやすくなる |
| 統一インターフェース | 資源の識別・表現による操作・自己記述的メッセージ・HATEOAS の 4 制約 | どの相手にも同じやり方が通じるようにそろえること | REST を REST たらしめる中心の制約 |
| HATEOAS | 次に可能な操作へのリンクを応答自体に含める制約 | 次に何ができるかを、返事の中に一緒に入れる | 実装されている API は少ない。要求する前に必要性を確認する |
| 冪等性（Idempotency） | 同じ要求を何度実行しても、意図した結果が変わらない性質 | 何回やっても同じ結果になること | 表記は「冪等」に統一する（「べき等」と混ぜない） |
| 冪等キー（Idempotency Key） | 再送を同一要求と判定するために、要求へ付ける一意な識別子 | 同じ依頼だと見分けるために付ける、ひとつだけの札 | 決済など POST の二重実行を防ぐ定番手段 |
| 安全なメソッド（Safe） | サーバの状態を変えないことが期待される HTTP メソッド | 読むだけで、何も書き換えない呼び出し | GET / HEAD / OPTIONS / TRACE。安全なら冪等でもある |
| バージョニング | 互換性のない変更に備え、API の版を区別できるようにすること | 作りを変えても古い呼び方が壊れないよう、版を分ける | URL 埋め込みとヘッダ指定がある。方式を先に決める |
| 後方互換性 | 新しい実装が、古い呼び出し側をそのまま動かせる性質 | 新しくしても、前からの呼び出しがそのまま動く | 「上位互換」と言い換えない。意味がずれる |
| 前方互換性 | 古い実装が、新しい形式の入力を壊れずに扱える性質 | 古いままでも、新しい形の入力で落ちない | 未知フィールドを無視する設計が典型 |
| 破壊的変更（Breaking Change） | 利用側の修正なしでは動かなくなる変更 | 直してもらわないと、使う側が動かなくなる変更 | 必須項目の追加・型変更・項目削除が代表例 |
| 非推奨（Deprecated） | まだ動くが、将来削除する予定であると宣言された状態 | まだ使えるが、いずれ消すと予告してある状態 | 削除予定日を具体的な日付で示す |
| 契約（Contract） | 呼び出し側と提供側が守ると約束した入出力と振る舞いの取り決め | 呼ぶ側と受ける側の間で決めた、守る約束ごと | 契約テストは、この約束が守られているかを確かめる |
| スキーマ | データの構造と型を機械が読める形で定義したもの | どんな項目がどんな形で入るかを、機械が読める形で書いたもの | DB のスキーマと API のスキーマを文脈で区別する |
| OpenAPI | HTTP API の仕様を記述する標準フォーマット | HTTP の API の仕様を、決まった書き方で書いたもの | 旧称 Swagger。現在は OpenAPI が正式名称 |
| GraphQL | 呼び出し側が必要な項目を指定して 1 回で取得できる問い合わせ言語 | 欲しい項目を指定して、必要な分だけまとめて取る仕組み | N+1 問題が起きやすく、DataLoader などの対策が要る |
| gRPC | スキーマ定義から生成したコードで通信する RPC 方式 | 定義から自動生成したコードで、直接呼び出すように通信する | Protocol Buffers とセット。ブラウザからは直接呼べない |
| ページネーション | 大量の一覧を一定件数ずつ分割して返す方式 | 一覧を一度に全部返さず、区切って返す | オフセット方式とカーソル方式で挙動が違う |
| レート制限（Rate Limiting） | 一定時間内の要求回数に上限を設けること | 決めた時間に呼べる回数に上限をつけること | 超過時は HTTP 429 を返し、再試行可能な時刻を示す |

## データモデリング

| 用語 | 意味 | ユーザーへの言い方 | 注意 |
|---|---|---|---|
| 正規化 | 重複を排除し、更新時の矛盾を防ぐようテーブルを分割する設計 | 同じ値を何か所にも持たないよう、表を分ける | 第 3 正規形までを実務の目安にする |
| 非正規化 | 参照性能のために、あえて重複を持たせる設計 | 読むのを速くするため、わざと同じ値を持たせる | 更新時の整合をどう保つかを必ず決めてから採る |
| 主キー | 行を一意に識別するための列または列の組 | 1 行を見分けるための、重ならない目印 | MySQL では主キー順に物理配置されるので選び方が性能に効く |
| 外部キー | 他テーブルの行を参照し、整合性を DB 側で保証する制約 | 別の表の行を指し、存在しない先を指せなくする決まり | アプリ側でのみ担保する運用もある。方針をそろえる |
| インデックス | 検索を高速化するために別に持つ、並べ替え済みの参照構造 | 探すのを速くするための、別立ての目次 | 増やすと書き込みが遅くなる。無条件に足さない |
| 複合インデックス | 複数の列をまとめて 1 つにしたインデックス | 複数の項目をまとめて 1 つにした目次 | 列の順番が効く。先頭列を使わない検索では効かない |
| カバリングインデックス | 必要な列がすべて含まれ、テーブル本体を読まずに済むインデックス | 目次だけで答えが出て、本体を見に行かずに済む状態 | MySQL の EXPLAIN で `Using index` と出れば成立している |
| トランザクション | 複数の操作を、全部成功か全部取り消しかのどちらかにする単位 | まとめて全部やるか、全部なかったことにするかの単位 | 長く保持するとロック競合が増える。短く区切る |
| ACID | トランザクションが満たすべき原子性・一貫性・独立性・永続性の 4 性質 | 途中で終わらない・矛盾しない・混ざらない・消えないの 4 条件 | 頭字語のまま使う。日本語に開かない |
| 分離レベル | 同時実行するトランザクションが互いをどこまで見るかの設定 | 同時に走る処理が、互いの途中経過をどこまで見るかの設定 | MySQL の InnoDB の既定は REPEATABLE READ |
| ダーティリード | 他のトランザクションの未確定の変更を読んでしまう現象 | まだ確定していない他人の変更を読んでしまうこと | READ UNCOMMITTED でのみ起きる |
| ファントムリード | 同じ条件で 2 回検索した間に、該当行が増減する現象 | 同じ条件で探したのに、2 回目だけ件数が変わること | 行の値変化（反復不能読み取り）とは別の現象 |
| 楽観ロック | 更新時にバージョンを照合し、競合していたら失敗させる方式 | ぶつからない前提で進め、ぶつかったときだけやり直す | 表記は「楽観ロック」に統一する（「楽観的ロック」と混ぜない） |
| 悲観ロック | 読み取りの時点で行を占有し、他の更新を待たせる方式 | 先に押さえてしまい、他の人を待たせる | MySQL では `SELECT ... FOR UPDATE` が該当する |
| 結果整合性 | 更新が全体に伝わるまで時間差があるが、最終的には一致する性質 | しばらくは食い違うが、そのうち必ずそろう | 表記は「結果整合性」に統一する（「最終的な一貫性」と混ぜない） |
| CAP 定理 | 分断が起きたとき、一貫性と可用性は同時には満たせないという定理 | 通信が切れたとき、正しさと動き続けることは両立しない | 平常時の話ではない。分断が起きたときだけの選択 |
| N+1 問題 | 一覧取得 1 回の後に、件数分の追加問い合わせが走ってしまう状態 | 一覧を取ったあと、1 件ずつ追加で問い合わせてしまう状態 | ORM と GraphQL で起きやすい。まとめ取得で解消する |
| マイグレーション | スキーマ変更を、順序づけた差分として適用・記録する仕組み | 表の形の変更を、順番どおりに当てて記録する仕組み | 元に戻す手順とセットで書く |
| 論理削除 | 行を消さず、削除済みを表すフラグや日時で表現する方式 | 実際には消さず、消したという印だけを付ける | 全クエリに条件追加が必要になる。採用前に必要性を確認する |
| レプリケーション | 同じデータの複製を別のインスタンスへ継続的に反映する仕組み | 同じ中身の写しを、別の場所に作り続ける | 読み取りを写し側に振ると遅延の影響を受ける |

## 実装品質・リファクタリング

| 用語 | 意味 | ユーザーへの言い方 | 注意 |
|---|---|---|---|
| 技術的負債 | 内部品質の不足によって、今後の変更に余計な労力がかかる状態 | 今のままだと、次に直すとき余計に時間がかかる状態 | Fowler は余計にかかった時間を「利息」と表現する |
| コードスメル | 設計上の問題がありそうだと示す、コード上の兆候 | すぐ壊れてはいないが、直したほうがよさそうな兆し | 必ず直すべきとは限らない。判断の入口として使う |
| リファクタリング | 外部から見た振る舞いを変えずに、内部構造を改善すること | 動きは変えずに、中の作りだけを整えること | 機能追加と同時にやらない。混ぜると差分が読めない |
| 循環的複雑度 | 制御フロー上の独立した経路の数で表す、コードの複雑さの指標 | 分岐がいくつ重なっているかを数えた、読みにくさの目安 | McCabe の定義。テストに必要な最低経路数の目安にもなる |
| 認知的複雑度 | 人が読むときの負荷を、入れ子の深さを重く数えて表す指標 | 人が追いかけるときのつらさを数値にしたもの | 循環的複雑度とは別の指標。混同しない |
| 神クラス（God Class） | 責務が集中しすぎて、変更のたびに触ることになる巨大なクラス | 何でも入っていて、何をするにも触ることになる大きな塊 | 批判語。分割方針とセットで指摘する |
| デッドコード | どの経路からも実行されないまま残っているコード | どこからも呼ばれず、残ったままになっているコード | 消すのをためらうならコメントではなく履歴に任せる |
| マジックナンバー | 意味の説明なしに直接書かれた定数値 | 何の値なのか説明のない、じかに書かれた数字 | 名前付き定数にするのが基本の対処 |
| テストダブル | テスト時に本物の代わりに差し込む部品の総称 | テストのときだけ差し替える、本物の代役 | Meszaros の分類では下の 5 種に分かれる |
| ダミー（Dummy） | 引数を埋めるためだけに渡され、実際には使われない代役 | 形をそろえるためだけに渡す、使われない値 | 呼ばれたら想定外なので、呼ばれたら落とす実装でもよい |
| フェイク（Fake） | 動作する実装を持つが、本番に使えない簡略版の代役 | ちゃんと動くが、本番では使えない簡易版 | インメモリ DB が典型。本物に近い検証ができる |
| スタブ（Stub） | あらかじめ決めた値を返すだけの代役 | 決めておいた答えを返すだけの代役 | 戻り値の検証に使う。呼ばれ方は問わない |
| スパイ（Spy） | 決めた値を返しつつ、呼ばれ方を記録する代役 | 答えを返しながら、どう呼ばれたかを記録しておく代役 | スタブの一種。後から呼び出し回数を確かめる |
| モック（Mock） | 期待する呼び出しを事前に設定し、その通りかを検証する代役 | 「こう呼ばれるはず」を先に決めて、その通りか確かめる代役 | 日本語で「モック」と言うとき全種の総称に使われがち。分類名として使う |
| テストピラミッド | 単体テストを厚く、上位のテストほど薄くするテスト構成の指針 | 細かいテストを多く、通しのテストは少なくする配分 | 逆三角形になった状態を「アイスクリームコーン」と呼ぶ |
| フレーキーテスト | 同じコードなのに、成功と失敗が不安定に入れ替わるテスト | 直していないのに、通ったり落ちたりするテスト | 放置すると CI の信頼が失われる。再実行で済ませない |
| カバレッジ | テスト実行時に通過したコードの割合 | テストがコードのどれだけを通ったかの割合 | 通ったことしか示さない。正しさの証明ではない |
| 副作用 | 戻り値以外の形で、外部の状態を読み書きすること | 値を返す以外に、外の何かを書き換えたり読んだりすること | I/O・グローバル変数・引数の書き換えが該当する |
| 純粋関数 | 同じ入力に対して常に同じ出力を返し、副作用を持たない関数 | 同じものを入れれば必ず同じ結果が出て、外に何もしない関数 | テストが楽になる。境界の内側に寄せる判断材料になる |
| 不変性（Immutability） | 生成後に内部状態を変更しない性質 | 作ったあとは中身を書き換えない作り | 並行処理の事故を減らす。値オブジェクトの原則 |
| 競合状態（Race Condition） | 複数の処理の実行順によって結果が変わってしまう状態 | 同時に動いたとき、順番しだいで結果が変わってしまう状態 | Go では `-race` フラグで検出できる |
| デッドロック | 互いに相手が持つ資源を待ち続け、どちらも進めなくなる状態 | 互いに相手の順番待ちになり、両方とも止まる状態 | ロックを取る順序を全体でそろえると防げる |
| スレッドセーフ | 複数の処理から同時に呼ばれても、結果が壊れない性質 | 同時に呼ばれても、結果がおかしくならない性質 | Go では goroutine safe と言うこともあるが意味は同じ |
| メモリリーク | 不要になった領域が解放されず、使用量が増え続ける状態 | 使い終わった分が返らず、使用量が増え続ける状態 | Go でも起きる。goroutine の取り残しが典型 |

## エラーとレジリエンス

| 用語 | 意味 | ユーザーへの言い方 | 注意 |
|---|---|---|---|
| 例外（Exception） | 通常の制御フローを中断して、上位へ処理を移す異常通知の仕組み | 処理を打ち切って、対処できる場所まで一気に戻す仕組み | Python / TypeScript はこちら。Go とは方式が違う |
| エラー値 | 異常を戻り値として返し、呼び出し側に明示的に扱わせる方式 | 異常を戻り値で返して、呼ぶ側に必ず見させるやり方 | Go はこちら。例外と混ぜて説明しない |
| エラーのラップ | 元のエラーを保持したまま、文脈の説明を付け足すこと | 元の原因を残したまま、どこで起きたかの説明を足すこと | Go は `fmt.Errorf("context: %w", err)`。`%w` を落とすと原因をたどれない |
| センチネルエラー | 比較で判定させるために、あらかじめ定義しておくエラー値 | あらかじめ決めておいて、見比べて判定するためのエラー | Go では `errors.Is` で比較する。文字列一致で判定しない |
| パニック（panic） | 回復手順のない異常として、処理を即座に巻き戻す機構 | 立て直せない異常として、その場で処理を打ち切る仕組み | Go では想定内の異常に使わない。ライブラリ境界で外へ漏らさない |
| リトライ | 一時的な失敗とみなして、同じ操作をやり直すこと | 一時的な不調とみなして、もう一度やり直すこと | 冪等でない操作に無条件で付けると二重実行になる |
| 指数バックオフ | 再試行の待ち時間を、失敗のたびに倍々で延ばす方式 | やり直すまでの間隔を、失敗するたびに長くしていくやり方 | 上限値を決めないと待ち時間が際限なく伸びる |
| ジッター | 再試行の待ち時間に乱数のばらつきを加えること | やり直す時刻をわざとばらけさせること | 指数バックオフとセットで使う。同時再試行の集中を防ぐ |
| サーキットブレーカー | 失敗が続いたら呼び出し自体を止め、一定時間後に試し直す仕組み | 失敗が続いたら呼ぶのをやめ、しばらくしてから様子を見る | Closed / Open / Half-Open の 3 状態。Fowler の定義 |
| タイムアウト | 応答を待つ上限時間を決め、超えたら打ち切ること | どこまで待つかを決めて、過ぎたらやめること | 既定値なしで外部呼び出しを書かない。無期限待ちは障害の連鎖を生む |
| バルクヘッド | 資源をあらかじめ区切り、1 か所の障害が全体に及ばないようにする方式 | 使える量を先に区切って、1 か所の不調が全部に広がらないようにする | 接続プールやワーカー数を用途別に分ける形で実現する |
| フォールバック | 本来の処理が失敗したときに使う、代わりの処理 | うまくいかなかったときに使う、代わりの手段 | 代替結果が業務上妥当かを必ず確認する |
| グレースフルデグラデーション | 一部が使えなくても、重要な機能だけは動かし続ける設計 | 一部が止まっても、大事なところだけは使えるようにしておく | 「縮退運転」と訳されることもある。カタカナで統一する |
| グレースフルシャットダウン | 処理中の要求を終えてから、新規受付を止めて停止すること | 途中の仕事を終わらせてから、受付をやめて落とすこと | Kubernetes では SIGTERM を受けてから猶予時間内に完了させる |
| フェイルファスト | 異常を検知した時点で、すぐ失敗させる方針 | おかしいと分かった時点で、すぐ止めてしまう方針 | 曖昧なまま進めて後で壊れるより原因を特定しやすい |
| カスケード障害 | 1 か所の障害が呼び出し元へ次々に波及して広がる現象 | 1 か所の不調が、呼んでいる側へ次々に広がること | タイムアウトとサーキットブレーカーで断ち切る |
| デッドレターキュー（DLQ） | 処理に失敗し続けたメッセージを退避しておく保管先 | 何度やっても処理できなかったものを、よけて置く場所 | 溜まったまま放置されやすい。監視をセットで用意する |
| 冪等な再送 | 同じメッセージが複数回届いても、結果が 1 回分にとどまる設計 | 同じ通知が二重に届いても、1 回分としてしか反映されない作り | 多くのキューは at-least-once。受け手側で重複を吸収する |
