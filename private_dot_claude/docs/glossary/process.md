# 開発プロセスの用語

この分野は、同じものを日本語と英語の両方で呼ぶため、訳語が揺れやすい。Git の履歴操作、GitHub のレビュー機能、スクラムのイベントは、
どれも「取り込む」「まとめる」「振り返る」のような曖昧な日常語に置き換えられがちで、置き換えた瞬間に別の操作と区別が付かなくなる。
Issue の階層を指す内部用語（leaf など）も、ユーザーには通じない。標準用語を 1 つ決めて使い、説明だけを日常語で書く。

## Git の基本操作と履歴

| 用語 | 意味 | ユーザーへの言い方 | 注意 |
|---|---|---|---|
| リポジトリ（repository） | ファイル一式と、その全変更履歴をまとめて保持する保管の単位 | ファイルと、これまでの変更の記録をまとめて置く場所 | 「レポジトリ」とは書かない |
| コミット（commit） | 変更のまとまりに、作者と日時と説明文を付けて履歴に記録したもの | ここまでの変更に説明を付けて保存した、1 件の記録 | スクラムの「確約（コミットメント）」とは別の語 |
| ワーキングツリー（working tree） | 実際にファイルを編集している、作業用ディレクトリの現在の状態 | いま自分が手元で編集しているファイルの状態 | 「作業ツリー」とも訳す、どちらでも通じる |
| ステージング（staging / index） | 次のコミットに含める変更だけをあらかじめ選び分けておく中間の置き場 | 次に保存する分だけを、先により分けておく状態 | `git add` した状態を指す、index とも呼ぶ |
| ブランチ（branch） | 履歴を枝分かれさせ、他の作業と混ぜずに変更を積んでいくための名前付きの分岐 | ほかの作業とぶつからないように、履歴を枝分かれさせたもの | — |
| HEAD | いま作業の対象にしているブランチ、またはコミットを指している参照 | 自分がいまどこで作業しているかを指している印 | — |
| detached HEAD | ブランチ名ではなく、特定のコミットを HEAD が直接指している状態 | どのブランチにも属さないまま作業している状態 | この状態で作ったコミットは名前が無く見失いやすい |
| マージ（merge） | 2 つのブランチが持つ変更を、1 つの履歴に合流させて片方へ取り込む操作 | 2 つの作業の内容を、1 つに合流させること | 「統合」「取り込み」と訳さず、マージで統一する |
| fast-forward | 取り込み先が取り込む側の履歴の延長線上にあるため、参照を進めるだけで済むマージ | 枝分かれしていないので、位置を進めるだけで済むマージ | Pro Git 日本語版も訳さず fast-forward と表記する |
| マージコミット | 合流元と合流先の 2 つを親に持ち、マージした事実そのものを記録するコミット | 合流したこと自体を残すために作られるコミット | `--no-ff` を付けると fast-forward でも作られる |
| コンフリクト（conflict） | 同じ箇所への異なる変更が両方から来て、Git がどちらを残すか決められない状態 | 同じ場所を別々に直したので、どちらを残すか人が決める状態 | 「競合」とも訳す、解消したら `git add` が要る |
| リベース（rebase） | 自分のコミット列を別のコミットの上に付け直し、履歴を一直線に並べ替える操作 | 自分の作業を、最新の状態の上に載せ直すこと | 公開済みのコミットには使わない、取り込みは merge |
| squash マージ | PR に含まれる複数のコミットを 1 つにまとめてから、ベースブランチへ取り込む方式 | 作業中の細かい記録を 1 つにまとめて取り込むこと | GitHub の日本語 UI では「スカッシュとマージ」 |
| cherry-pick | 別のブランチにある特定のコミットの変更だけを、いまのブランチに写し取る操作 | ほしい 1 件の変更だけを選んで持ってくること | ブランチ全体ではなく、コミット 1 件ずつ選ぶ |
| stash | 未コミットの変更を一時的に退避し、作業ディレクトリをきれいな状態に戻す仕組み | 途中の変更をいったんしまって、あとで戻すこと | 変更を捨てる `reset --hard` の代わりに使う |
| タグ（tag） | 特定のコミットに付ける、あとから動かない名前の参照 | ある時点に付ける、あとから動かない目印 | リリース版を指すのに使う、ブランチと違い進まない |
| fetch | リモートの最新の履歴を手元に取り寄せるだけで、作業中のファイルは変えない操作 | 最新の状況を取り寄せるだけで、手元はまだ変えないこと | — |
| pull | fetch したうえで、取り寄せた内容をいまのブランチにマージするところまで行う操作 | 最新を取り寄せて、手元にも反映するところまでやること | fetch との違いは、手元に反映するかどうか |
| push | 手元のコミットをリモートリポジトリへ送り、リモートのブランチを進める操作 | 手元の記録を、共有先へ送って反映させること | — |
| upstream（上流ブランチ） | そのブランチが既定で fetch と merge の相手にする、リモート側のブランチ | そのブランチが既定で相手にする、共有先のブランチ | フォーク元のリポジトリを指す用法もあるので文脈を見る |
| リモート追跡ブランチ | リモートのブランチが最後に見えた位置を、手元に控えておくための参照 | 共有先の状態を最後に見たときの控え | `origin/main` などがこれ、直接コミットしない |
| force push | リモートが持つ履歴を、手元の履歴で無条件に上書きするプッシュ | 共有先の記録を、手元の内容で強制的に置き換えること | 他人のコミットを消すので、既定では使わない |
| `--force-with-lease` | リモートが自分の知っている位置のままのときだけ通す、条件付きの force push | 自分が最後に見たときから変わっていなければ上書きする指定 | 他人の push があると失敗するので force より安全 |
| revert | 打ち消す内容のコミットを新しく積み、過去の変更を履歴を残したまま取り消す操作 | 過去の変更を打ち消す記録を、あとから足すこと | 履歴を消さない、reset とは別の操作 |
| reset | ブランチの先端を別のコミットへ動かし、どこまでを記録済みとするかを変える操作 | どこまでを保存済みとするかを巻き戻すこと | `--hard` は編集中の内容も消えるので使わない |
| reflog | HEAD やブランチが過去に指していた位置を残す、手元だけの移動の記録 | どこを指していたかの記録、消したものを取り戻せる | 手元にしか無く、一定期間で消える |
| worktree | 1 つのリポジトリから複数の作業ディレクトリを切り出し、同時に開いておく仕組み | 同じリポジトリを別々の場所で開き、並行して作業する仕組み | 別々の Issue を同時に進めるときに使う |
| amend | 直前のコミットを作り直し、内容や説明文を差し替える操作 | 直前の記録をいったん取り消して、作り直すこと | push 済みだと force push が要るので既定では使わない |
| `.gitignore` | 履歴の追跡対象から外すファイルのパターンを列挙した設定ファイル | 履歴に入れたくないファイルを書いておく設定 | すでに追跡中のファイルには効かない |
| Conventional Commits | コミットの説明文を `type(scope): 要約` の形に定めた、記述の仕様 | コミットの説明文の書き方を決めた取り決め | `feat` がマイナー、`fix` がパッチの更新に対応する |

## GitHub とレビュー

| 用語 | 意味 | ユーザーへの言い方 | 注意 |
|---|---|---|---|
| Pull Request（PR） | ブランチの変更をベースブランチへ取り込む提案と、その議論を行う単位 | 変更を取り込んでほしいという提案と、その話し合いの場 | GitLab では Merge Request と呼ぶ |
| ベースブランチ | その PR の変更を最終的に取り込む先として、PR に指定してあるブランチ | その変更を、最後にどこへ戻すかとして指定したブランチ | ブランチを切った元と一致しないことがある |
| ドラフト PR（draft） | まだレビューを求めず、作業中であることを明示した状態の PR | まだ途中なので見なくてよい、と示してある PR | レビュー依頼には Ready for review への切り替えが要る |
| レビュアー（reviewer） | その PR の内容を確認し、取り込んでよいか判断するよう指名された人 | 変更の中身を見て、良し悪しを判断するよう頼まれた人 | assignee（進める担当者）とは役割が違う |
| assignee（担当者） | その Issue や PR を進めきる責任を持つ人として割り当てられた人 | それを最後まで進める責任を持つ人 | レビュアーと混同しない、両方付けることもある |
| approve（承認） | レビューで、この内容のまま取り込んでよいと表明すること | この内容のまま取り込んでよい、と表明すること | 自分が作った PR には付けられない |
| request changes（変更を要求） | レビューで、直してほしい点があるとして PR を作者へ差し戻すこと | 直してほしい点があるとして、いったん返すこと | ブランチ保護の設定によってはマージが止まる |
| suggestion（変更の提案） | レビューコメントに具体的な修正案を埋め込み、押すだけで反映できる形式 | 直し方をコメントに書いて、押すだけで反映できる形 | 取り込むとコミットが 1 件増える |
| 会話の解決（resolve conversation） | レビューコメントのやり取りに対応済みの印を付け、表示を畳むこと | 対応が済んだ指摘に、済みの印を付けて閉じること | 原則として、指摘した側が解決する |
| CODEOWNERS | パスごとにレビュー責任者を割り当てる、リポジトリ内の設定ファイル | どのファイルは誰が見るかを決めた一覧 | ルート・`.github/`・`docs/` のいずれかに置く |
| マイルストーン | 期限を決めた区切りに、複数の Issue と PR をまとめて進捗を見る仕組み | 期限を決めて、そこまでにやる分をまとめたもの | — |
| ラベル | Issue と PR を色付きの名前で分類し、絞り込みに使うための印 | 分類のために付ける、名前の付いた印 | Issue Type と役割が重なるので使い分けを決める |
| merge queue（マージキュー） | マージ待ちの PR を順に並べ、最新のベースで検証してから取り込む仕組み | 順番待ちに並べ、最新の状態で確かめてから取り込む仕組み | 直前に別の PR が入って壊れるのを防ぐ |
| nit | レビューで、直さなくても構わない細かい指摘であることを示す前置き | 直さなくてもよい細かい指摘です、という前置き | 日本語では「細かい点ですが」と書けば足りる |
| LGTM | Looks Good To Me の略で、問題ないという意思を短く示す言い回し | 「自分は良いと思う」を短く言ったもの | 正式な承認は approve で行う、LGTM は表明だけ |
| GitHub Projects | Issue と PR を表やボードに並べ、期間や状態で進捗を管理する機能 | Issue を一覧やボードに並べて、進み具合を見る道具 | リポジトリ単位と Organization 単位の 2 種類がある |
| Iteration（フィールド） | GitHub Projects で、作業が属する期間の区切りを表す日付の属性 | その作業がどの期間の分かを示す欄 | スクラムのスプリントを表すのに使う |
| triage（トリアージ） | 届いた Issue と PR を、緊急度と種類で仕分けして担当を決めること | 届いたものを、急ぎ具合と種類で仕分けすること | — |

## Issue の階層

Epic / Feature / Task は上から下への包含関係にある。実装と PR が対応するのは、いちばん下の Task だけ。

| 用語 | 意味 | ユーザーへの言い方 | 注意 |
|---|---|---|---|
| Issue | 作業・不具合・要望の 1 件を表し、議論と進捗の追跡の単位になるもの | やることや不具合を、1 件ずつ書いて追いかける単位 | — |
| Issue Type | Epic / Feature / Task / Bug のように、その Issue の種類を示す属性 | その Issue がどの粒度と種類かを示す区分 | ラベルとは別、Organization 共通の属性として設定する |
| Epic | 複数のリリースにまたがる大きな目的をまとめる、いちばん上の階層の Issue | いくつもの機能をまとめた、いちばん大きなまとまり | それ自体は実装せず、下に Feature をぶら下げる |
| Feature | Epic を分割し、利用者に価値が届く 1 つのまとまりを表す中間の階層の Issue | 利用者に届く形になる、1 つのまとまった機能 | 直接 PR で閉じず、下の Task に分けて進める |
| Task | それ以上分割せず、1 つの PR で完了できる最小の作業を表す Issue | それ以上分けずに、そのまま着手できる最小の作業 | PR が `Closes` で閉じるのは、原則この階層 |
| Sub-issue（サブイシュー） | 親 Issue にぶら下げ、親側で進捗を集計できるようにした子の Issue | 親にぶら下げて、まとめて進み具合を見る子の Issue | 入れ子は 8 階層まで、親 1 件につき 100 件まで |
| 末端の Issue | 子を持たず、実際の作業と PR が 1 対 1 で対応する最下層の Issue | 下にこれ以上分かれていない、実作業に対応する Issue | 内部用語の「leaf」を使わず、この語か Task と書く |
| `Closes` | PR 本文に書くと、既定ブランチへのマージ時にその Issue を自動で閉じるキーワード | マージしたら、その Issue も自動で閉じるという書き方 | `close` `fixes` `resolves` なども同じ働きをする |
| `Refs` | 関連する Issue を参照するだけで、マージしても閉じない書き方 | 関係があるとだけ示し、閉じはしない書き方 | GitHub の自動クローズ対象外、逃げに使わない |

## ブランチ戦略とリリース

| 用語 | 意味 | ユーザーへの言い方 | 注意 |
|---|---|---|---|
| GitFlow | `develop` を常設し、feature / release / hotfix を用途別に使い分けるブランチ運用 | 常設の開発用ブランチを置き、用途別にブランチを分ける進め方 | `develop` があるかどうかで GitHub Flow と使い分ける |
| GitHub Flow | 常設ブランチを `main` だけにし、feature から PR で `main` へ戻すブランチ運用 | 本流を 1 本だけにして、そこへ PR で戻す進め方 | `develop` が無いリポジトリではこちらを使う |
| トランクベース開発 | 短命のブランチだけを使い、1 日以内に本流へ統合し続けるブランチ運用 | ブランチを長く残さず、毎日のように本流へ戻す進め方 | 未完成の機能はフィーチャーフラグで隠して出す |
| feature ブランチ | 1 つの機能や修正のために切り、取り込み後に削除する作業用のブランチ | 1 つの作業のために作って、終わったら消すブランチ | 命名に Issue 番号を含める（例 `feature/123-add-auth`） |
| release ブランチ | リリース準備のために切り、公開後に本流と開発用の両方へ戻すブランチ | 公開の準備作業だけをするためのブランチ | 分岐元は develop、マージ先は main と develop の両方 |
| hotfix ブランチ | 公開中の不具合を緊急で直すため、`main` から切るブランチ | 公開中の不具合を、急いで直すためのブランチ | main と develop の両方へ戻す必要がある |
| 分岐元 | そのブランチを作るときに、基点にしたブランチ | どこからそのブランチを出したか | マージ先と食い違うのは release ブランチだけ |
| マージ先 | その PR の変更を、最終的に取り込むことになるブランチ | その変更を、最後にどこへ戻すか | 分岐元と混同しない、両者は別々に決まる |
| セマンティックバージョニング（SemVer） | `メジャー.マイナー.パッチ` の 3 つの数で、互換性の変化を表す版番号の規約 | 番号の上げ方で、どれだけ大きな変更かを伝える決まり | 互換性を壊したらメジャー、機能追加はマイナー |
| メジャーバージョン | これまでの使い方が通らない変更を入れたときに上げる、いちばん左の数 | これまでの使い方が通らなくなったときに上げる数 | 上げたらマイナーとパッチは 0 に戻す |
| マイナーバージョン | 互換性を保ったまま機能を足したときに上げる、真ん中の数 | 今までどおり使えて、機能が増えたときに上げる数 | 上げたらパッチは 0 に戻す |
| パッチバージョン | 互換性を保った不具合修正だけを入れたときに上げる、いちばん右の数 | 不具合を直しただけのときに上げる数 | — |
| プレリリース版 | `1.0.0-rc.1` のように、正式版の前に試験目的で出す版 | 正式に出す前の、お試しの版 | ハイフンの後ろに識別子を書く、正式版より前に並ぶ |
| BREAKING CHANGE | これまでの使い方が通らなくなる変更であることを明示する、コミットの表記 | これまでの使い方が通らなくなる変更です、という印 | `feat!:` と `!` を付けるか、フッターに書く |
| 変更履歴（CHANGELOG） | 版ごとに、利用者が知るべき変更を時系列で並べて記録したファイル | 版ごとに何が変わったかを、順に並べた一覧 | 追加・修正など種類ごとに分けて書く |
| `Unreleased` | まだ公開していない変更をためておく、変更履歴の先頭の節 | まだ出していない分を、先頭にためておく場所 | 公開時に、その版の番号の節へ移す |
| リリースノート | その版で何が変わったかを、利用者向けにまとめた告知の文書 | 今回の公開で何が変わったかのお知らせ | 変更履歴は積み上げ、リリースノートは 1 回分 |
| バックポート | 新しいブランチで直した内容を、古い版のブランチへも当て直すこと | 新しい方で直した内容を、古い方にも当てること | cherry-pick で行うことが多い |

## CI/CD

| 用語 | 意味 | ユーザーへの言い方 | 注意 |
|---|---|---|---|
| CI（継続的インテグレーション） | 変更を頻繁に本流へ統合し、その都度ビルドとテストを自動で回す進め方 | 変更するたびに、自動で組み立てて試す進め方 | 「継続的インテグレーション」が定訳、訳さず CI でも可 |
| CD（継続的デリバリー / デプロイ） | 検証を通った変更を、いつでも、または自動で本番へ出せる状態に保つ進め方 | いつでも出せる状態を保つ、または自動で出す進め方 | デリバリーは承認あり、デプロイは承認なしで出る |
| パイプライン | ビルドからテスト、配置までを定めた順序で自動実行する、一連の処理 | 組み立てから配置までを、決めた順に自動で流す仕組み | GitHub Actions ではワークフローと呼ぶ |
| ワークフロー（workflow） | GitHub Actions で、1 つ以上のジョブを実行する自動処理の定義 | 何をどの順で自動実行するかを書いた定義 | `.github/workflows/` に YAML で置く |
| ジョブ（job） | 同じランナーの上で順に実行される、一連のステップのまとまり | 1 台の実行環境で、まとめて動かす処理のかたまり | ジョブ同士は既定で同時に走る |
| ステップ（step） | ジョブの中で 1 回だけ実行される、コマンドまたはアクション | ジョブの中の、1 つ分の手順 | — |
| アクション（action） | ワークフローから呼び出して使える、再利用を前提に作られた処理の部品 | 使い回せるように作られた、処理の部品 | バージョンを固定して呼び出す |
| ランナー（runner） | ワークフローのジョブを実際に実行するサーバー | 処理を実際に動かすサーバー | GitHub 提供とセルフホストの 2 種類がある |
| 成果物（artifact） | ワークフローが生成し、あとからダウンロードできる形で保存しておくファイル | 実行の結果できたファイルを、あとで取れるように残したもの | スクラムの「作成物」とは別語なので訳し分ける |
| キャッシュ（cache） | 依存パッケージなど取得に時間がかかるものを保存し、次回に使い回す仕組み | 毎回取り直すと遅いものを、取っておいて使い回す仕組み | 成果物と違い、速くするためだけに使う |
| マトリクス実行（matrix） | 言語やバージョンの組み合わせごとに、同じジョブを並列に走らせる書き方 | 条件の組み合わせごとに、同じ検査を並べて走らせること | 組み合わせの数が、そのまま実行の数になる |
| 必須チェック（required status check） | 合格しないとマージを許可しないと定めた、自動チェックの項目 | 通らないとマージできない、と決めた検査 | チェック名が一致しないと永久に待ち続ける |
| ブランチ保護 | 特定のブランチへの直接 push やマージの条件を制限する設定 | 大事なブランチに、勝手に入れられないようにする設定 | 新しい書き方はルールセット |
| ルールセット（ruleset） | 複数の保護ルールを重ねて適用できる、ブランチ保護の新しい方式 | 保護の決まりを重ねて効かせられる、新しいやり方 | 旧方式は 1 ブランチに 1 ルールしか効かない |
| デプロイ承認 | 環境へ配置する前に、指名された人の承認を待たせる設定 | 本番へ出す前に、人の承認を 1 回はさむ設定 | GitHub では environment の保護ルールで設定する |

## テスト

| 用語 | 意味 | ユーザーへの言い方 | 注意 |
|---|---|---|---|
| 単体テスト（unit test） | 関数やクラスなど小さな単位が、意図どおり動くことを確かめるテスト | 部品を 1 つずつ取り出して、正しく動くか確かめる試験 | 「ユニットテスト」も同義、実装の詳細ではなく振る舞いを試す |
| 結合テスト（integration test） | 自分のコードと、DB や外部 API など外側との接続が動くことを確かめるテスト | 自分のコードと、外とのつなぎ目が動くか確かめる試験 | 「統合テスト」も使われるが「結合テスト」を標準にする |
| E2E テスト | 利用者と同じ経路をたどり、システム全体が通しで動くことを確かめるテスト | 利用者と同じ手順で、最初から最後まで通して試すこと | 安定しにくく維持費が高いので、数を絞って使う |
| テストピラミッド | 単体を多く、結合を中くらい、E2E を少なくする、テスト量の配分の指針 | 小さい試験を多く、通しの試験を少なくする配分の考え方 | 逆向きになった状態はアイスクリームコーンと呼ぶ |
| 回帰テスト（regression test） | 以前直した不具合や既存の動作が、再び壊れていないことを確かめるテスト | 前に直したところが、また壊れていないか確かめる試験 | 「リグレッションテスト」も同義 |
| スモークテスト | 配置の直後に、主要な機能が最低限動くかどうかだけを短時間で確かめるテスト | 出した直後に、とりあえず動くかだけを手早く見る試験 | 細部は見ない、通ってから本格的な検証に進む |
| カバレッジ（網羅率） | テストの実行がコードのどれだけを通ったかを、割合で示す指標 | テストがコードのどれくらいを通ったかの割合 | 高くても正しさは保証しない、目標値の独り歩きに注意 |
| フレーキーテスト（flaky test） | コードを変えていないのに、成功と失敗が入れ替わってしまうテスト | 直していないのに、通ったり落ちたりする試験 | 「不安定なテスト」とも言う、放置すると CI が信じられなくなる |
| テスト駆動開発（TDD） | 失敗するテストを先に書き、通してから整える順序で進める開発の進め方 | 先にテストを書いて、それを通す形でコードを書く進め方 | Red / Green / Refactor の 3 手順を繰り返す |
| 受け入れ条件（Acceptance Criteria） | その Issue が完了したと言えるために満たすべき、検証可能な条件 | 何が出来たら終わりと言えるかを、確かめられる形で書いたもの | 「AC」と略す、全 Issue 共通の完成の定義とは別 |
| 受け入れテスト | 受け入れ条件を満たしているかを、依頼した側の視点で確かめる検証 | 頼んだとおりに出来ているかを、頼んだ側の目で確かめること | 受け入れ条件とセットで用意する |
| 境界値 | 条件が切り替わる境目の、すぐ内側と外側にあたる入力値 | ちょうど境目になる値と、その前後の値 | 不具合が集中するので必ず試す |
| モック（mock） | 本物の代わりに差し込み、正しく呼ばれたかどうかまで検証する偽の部品 | 本物の代わりに置き、正しく呼ばれたかまで見る偽物 | 呼ばれ方を見ないものはスタブと呼び分ける |
| スタブ（stub） | 決まった値を返すだけの、本物の代わりに差し込む偽の部品 | 決まった答えを返すだけの、代わりの部品 | モックと役割が違うので混同しない |
| フィクスチャ（fixture） | テストを走らせる前に用意しておく、決まった初期データや初期状態 | テストの前に用意しておく、決まったデータ | — |
| 契約テスト（contract test） | 呼ぶ側と呼ばれる側が、取り決めどおりの形でやり取りしているか確かめるテスト | つなぐ両者が、決めた形を守っているか確かめる試験 | E2E を減らす代わりに置く |
| 静的解析 | コードを実行せずに、規約違反や不具合の兆候を機械的に見つけること | 動かさずに、書き方の問題を機械で見つけること | リンター（lint）はこの一種 |
| フォーマッタ | コードの見た目を決まった形にそろえて書き換える道具 | 書き方の見た目を、自動でそろえる道具 | 動作は変えない、リンターとは役割が違う |

## アジャイル・スクラム

| 用語 | 意味 | ユーザーへの言い方 | 注意 |
|---|---|---|---|
| スプリント | 1 か月以内の決まった長さで区切る、スクラムの作業期間 | 決まった長さで区切った、作業の期間 | 前が終わり次第すぐ次が始まる、途中で延ばさない |
| スプリントプランニング | スプリントの起点で、そのスプリントで行う作業の計画を立てるイベント | そのスプリントで何をやるかを決める会 | 1 か月のスプリントなら最大 8 時間 |
| デイリースクラム | 開発者が毎日 15 分で、スプリントゴールへの進捗を検査するイベント | 毎日 15 分、進み具合を確かめる集まり | 「朝会」は通称、上長への進捗報告会にしない |
| スプリントレビュー | スプリントの成果をステークホルダーに示し、次の適応を決めるイベント | 出来たものを関係者に見せて、次を決める会 | 発表会にせず、一緒に考える場にする |
| スプリントレトロスペクティブ | スプリントの進め方を検査し、品質と効果を高める方法を計画するイベント | やり方を振り返り、次に良くする点を決める会 | 公式訳はこの表記、「振り返り」「レトロ」は通称 |
| プロダクトバックログ | プロダクトの改善に必要なものを、順番に並べた唯一の一覧 | これからやることを、優先順に並べた一覧 | 「バックログ」だけだとスプリントバックログと紛れる |
| スプリントバックログ | スプリントゴールと、選んだ項目と、達成までの計画をまとめたもの | このスプリントでやる分と、その進め方 | 開発者のための計画、期間中に更新してよい |
| プロダクトバックログアイテム（PBI） | プロダクトバックログに並ぶ、1 件分の項目 | やることの一覧に並ぶ、1 件分 | 公式訳は「アイテム」、「項目」とは書かない |
| リファインメント | 項目を分割し、説明と並び順と大きさを足して、選べる状態にしていく活動 | 一覧の 1 件ずつを、着手できる細かさまで整えていくこと | 正式なイベントではなく、継続的に行う活動 |
| スプリントゴール | そのスプリントで達成すべき、唯一の目的 | そのスプリントで何を成し遂げるかの、1 つの狙い | 作業一覧ではなく、目的を 1 文で書く |
| プロダクトゴール | プロダクトの将来の状態を表す、スクラムチームの長期の目標 | この製品をどこへ持っていくかという、長期の目標 | プロダクトバックログの中に含める |
| インクリメント | 完成の定義を満たし、これまでの成果に積み上がった、利用可能な成果 | 今回できて、すぐ使える状態になった分 | 完成の定義を満たさないものは、これに含めない |
| 完成の定義（Definition of Done） | 成果が品質基準を満たしていると言える状態を示す、正式な記述 | これを満たしていれば完成と言える、全員共通の基準 | 公式訳は「完成の定義」、「完了の定義」とは書かない |
| Definition of Ready（DoR） | 着手してよい状態と言えるために、その Issue が満たすべき条件 | 着手してよいと言える状態かどうかの、判断の条件 | スクラムガイドには無い、チーム独自の取り決め |
| 作成物（Artifacts） | プロダクトバックログ、スプリントバックログ、インクリメントの 3 つの総称 | スクラムで作り、見せ合う 3 つのもの | 公式訳は「作成物」、CI の「成果物」と訳し分ける |
| ストーリーポイント | 作業の大きさを、所要時間ではなく相対的な数で見積もるための単位 | かかる時間ではなく、相対的な大きさで表した見積もり | スクラムガイドには無い、チームをまたいで比べない |
| ベロシティ | 1 スプリントで完成させたストーリーポイントの合計値 | 1 スプリントでどれだけ終えられたかの量 | スクラムガイドには無い、他チームとの比較に使わない |
| キャパシティ | そのスプリントで、チームが作業に使える時間の見込み | そのスプリントで使える時間の見込み | 実績を表すベロシティと混同しない |
| バーンダウンチャート | 残りの作業量が、時間とともにどう減っているかを示す図 | 残りがどのくらいのペースで減っているかを示す図 | 見通しの補助であり、実際の検査の代わりにはならない |
| ブロッカー | 他の要因が解消されるまで、その作業を進められない状態 | 先に何かが片付かないと、先へ進めない状態 | スクラムガイドの公式訳は「障害物」 |
| ステークホルダー | その成果に利害を持ち、フィードバックを返す立場の人 | その成果に関わりがあり、意見をくれる人 | 「関係者」と訳しても通じる |
| タイムボックス | イベントに設けた、延長しないと決めた上限の時間 | 延ばさないと決めておく、会の持ち時間 | 早く終わるのは構わない、延ばすのが違反 |

## 文書と意思決定

| 用語 | 意味 | ユーザーへの言い方 | 注意 |
|---|---|---|---|
| ADR（アーキテクチャ決定記録） | 1 つの設計上の決定と、その理由と結果を記録した文書 | なぜその作りにしたのかを、1 件ずつ残した記録 | 決定 1 件につき 1 ファイル、後から書き換えず状態を変える |
| RFC | 実装の前に案を文書で回し、関係者の意見を集めるための提案書 | 先に案を書いて、皆の意見を集めるための文書 | RFC が決定の前、ADR が決定の記録 |
| 仕様駆動開発（SpecDD） | 仕様書を先に固め、そこから Issue と実装を導いていく進め方 | 先に仕様を決め、そこから作業と実装に落としていく進め方 | 要件が Epic、設計が Feature、作業が Task に対応する |
| 前提（assumption） | 正しいと仮に置いて設計を進める、後から崩れうる条件 | 正しいと仮に置いて進めている条件 | 崩れたら設計を見直すので、必ず文書に書き出す |
| 制約（constraint） | 自分たちでは変えられない条件として、選べる案を狭めるもの | 変えられないので、取れる案を絞り込む条件 | 前提と違い、自分たちの判断では動かせない |
| スコープ | その作業で対応すると決めた範囲 | どこまでをやると決めたかの範囲 | 対象外も併せて書くと、誤解が減る |
| スコープクリープ | 合意した範囲が、都度の追加によって少しずつ膨らんでいくこと | やることが、少しずつなし崩しに増えていくこと | 気付いた時点で Issue を分けて切り出す |
| 非機能要件 | 性能・可用性・安全性など、動作そのもの以外に求める品質の条件 | 動くかどうかではなく、どれだけ良く動くかの条件 | 機能要件と対で書く、測れる数値で書く |
| トレーサビリティ | 要件から Issue、PR、テストまでを相互にたどれる状態 | どの要件が、どの作業とテストに対応するかをたどれること | `Closes` による PR と Issue のリンクがこれを支える |
| 意思決定の背景（context） | その決定を必要とした状況と、比較した選択肢を書き残した部分 | なぜ決める必要があったのか、何と比べたのかの記述 | 結論だけ残すと、後から見直せなくなる |
