# やさしい日本語の言い換え例

`rules/easy-japanese.md` の R1〜R9 の言い換え例と置き換え表。常時読み込みはされない。判断に迷ったときに読む。

## R1: 一文を短くする

- 通常: 「申請内容に不明な点がある場合は確認のため担当者から連絡することがあります」
- やさしい: 「申請内容が分からないときは、担当者から連絡します。そのときは確認に協力してください」

## R2: 主語と動作主を明示し、能動態で書く

- 通常: 「必要書類は窓口で確認されたあと返却されます」
- やさしい: 「窓口の担当者が必要書類を確認します。確認したあと、担当者が書類を返します」

`AskUserQuestion` の質問文は本文と切り離して表示される。番号や指示語を主語にすると、何の話か分からない。

- 通常: 「#7001 の進め方をどうしますか」
- やさしい: 「Percona Toolkit を導入する Issue（#7001）は、同じデプロイ定義を触る承認者設定の Issue（#6863）とどちらを先に進めますか」
- 通常: 「このドラフトで進めてよいですか」
- やさしい: 「事業部向けの Slack メッセージ（お客様の声の食い違い 46 行の案内）を、このドラフトのまま送ってよいですか」
- 通常: 「PR 2 本のマージは、どうしますか？」
- やさしい: 「店舗ページの二重表示を直す PR（#6445）と SEO の題名を直す PR（#6520）は、どちらを先にマージしますか」

## R3: 3 つ以上は箇条書きにする

- 通常: 「申請のときは、本人確認書類、申請書、必要書類のコピー、手数料を持ってきてください」
- やさしい:
  > 申請のときは、次のものを持ってきてください。
  > - 本人確認書類
  > - 申請書
  > - 必要書類のコピー
  > - 手数料

## R4: 外来語はビジネス一般語だけ日本語に言い換える

- 通常: 「エビデンスをアサインしてオーソライズしてください」
- やさしい: 「証跡を担当者に割り当てて承認してください」
- 技術文脈はそのまま: 「main ブランチに直接コミットしないでください」

IT の標準用語は言い換えの対象外。カタカナや英語のまま書く。標準用語を和語に置き換えると、R4 を守ったつもりで意味の通らない造語になる。

| 和語に置き換えた例（不可） | 標準用語（可） |
|---|---|
| 移行元の写しを読むテスト | 移行元のミラーを読むテスト |
| 3 本とも飛ばしに裏返す | 3 本ともスキップに切り替える |
| 携帯の名乗りで確認アクセスする | モバイルの User-Agent で確認アクセスする |
| 横送りの部品を足す | カルーセルを追加する |
| dev への配信 | dev へのデプロイ |
| 題名の帯 / 絵の全数確認 | タイトルのバナー / 画像の全件確認 |
| DB への経路を開く | DB への接続を許可する |

判定の目安: その語で検索して IT の記事が出るか。出なければ和語の造語なので、英語かカタカナの標準用語に戻す。

## R5: 二重否定を使わない

- 通常: 「在留カード以外は必要ありません」→ やさしい: 「在留カードを持ってきてください」
- 通常: 「対応していないことはありません」→ やさしい: 「対応しています」

## R6: 期限・数量は具体値で

- 通常: 「担当者が午前 11 時ごろに連絡します」→ やさしい: 「担当者が午前 10:30〜11:30 の間に連絡します」
- 通常: 「いくつかのファイルを修正しました」→ やさしい: 「3 ファイル（src/foo.ts / src/bar.ts / test/baz.test.ts）を修正しました」

## R7: 名詞句の連結より動詞句で書く

動作名詞（ヒアリング / 通読 / 整備 / 把握 / 分析 / 共有 / 確認 / 承認 / レビュー）を名詞のまま並べると、動作主・対象・動作が圧縮されて読み手が開き直す負担になる。

- 通常: 「現サイト操作 + legacy-analysis 通読 + PdM/BE ヒアリングを通じて整備する」
- やさしい: 「現サイトを操作し、legacy-analysis を読み、PdM と BE にヒアリングして整備する」
- 通常: 「Home カンプのステークホルダーレビュー後に展開」
- やさしい: 「Home カンプをステークホルダーがレビューし、承認されてから展開する」

| 名詞句 | 動詞句 |
|---|---|
| XX ヒアリング | XX にヒアリングする / XX に聞く |
| XX レビュー | XX をレビューする / XX を見直す |
| XX 通読 | XX を読む / XX に目を通す |
| XX 把握 | XX を把握する / XX を理解する |
| XX 整備 | XX を整備する / XX を揃える |
| XX 分析 | XX を分析する |
| XX 共有 | XX を共有する |
| XX 承認 | XX を承認する / XX の承認を得る |
| XX 確認 | XX を確認する |
| XX 制作 | XX を制作する |
| XX 反映 | XX を反映する |

## R8: project 固有名詞は役割を併記する

名称だけだと、project に新しく入った人や別チームのレビュアーは別タブで調べないと意味が取れない。

- 通常: 「`legacy-analysis` を読む」→ やさしい: 「現サイト機能の分析資料（`legacy-analysis`）を読む」
- 通常: 「`target-persona.md` にターゲット属性が記載されている」→ やさしい: 「`target-persona.md`（ターゲット属性）にターゲット属性が記載されている」
- 通常: 「`mypage-bookings` テーブルを参照する」→ やさしい: 「予約データを保存する `mypage-bookings` テーブルを参照する」
- ディレクトリ名（`research/` など）は対象外

判定の目安: 「英単語の組み合わせを頭の中で訳さないと意味が取れないか」を自問する。拡張子付きの個別ファイル名は原則すべて併記する。併記の形は「`name.md`（役割）」を基本にし、名称を主役にしたいときは「役割（`name.md`）」でもよい。

## R9: 総称語より対象物の用語で書く

総称語は「具体的に何を指すか」の解決を読み手に強いる。対象が 1 つに決まる場面では抽象化に意味がない。

- 通常: 「leaf をコピーする」→ やさしい: 「WP-Cron スケジューラ定義（Lambda / EventBridge Scheduler）をコピーする」
- 通常: 「caller を新設する」→ やさしい: 「ECS クラスタ定義を新設する」
- 通常: 「CI は leaf ごとに plan を走らせる」→ やさしい: 「CI は Terragrunt 定義（caller）ごとに plan を走らせる」（全対象をまとめて指す総称用途。leaf は使わず caller に置き換え、役割の説明を前置する）

「leaf」は総称用途でも使わない。ディレクトリなら「末端のディレクトリ」「サイト別の定義」、Issue なら「子を持たない末端の Issue」と書く。
