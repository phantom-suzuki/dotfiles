# 作業モードを決めてから計画する

実装・修正の依頼を受けたら、着手前に作業モードを 1 つ決め、モードに合わせて作業範囲を絞る。最終結果が同じでも、フェーズによって求められる進め方は違う。広く考慮しすぎて、頼まれていない作業まで広げるのを防ぐための規律である。

## 3 つのモード

| モード | 優先するもの | 典型の場面 |
|---|---|---|
| 開発 | 技術的合理性・保守性と予定の両立 | 新規開発・リファクタリング・設計変更 |
| 運用改修 | 対応の速さと差分の小ささ。既存の構造と挙動を変えない | 運用中の小さな改修・改善・設定変更 |
| 緊急復旧 | 復旧の速さ。設計の良し悪しは後回し | 本番障害・致命的な不具合 |

## 判定の順

1. ユーザーの言葉で決める。「最小で」「とりあえず」「さっと」は運用改修。「障害」「落ちている」「hotfix」「至急」は緊急復旧。「新規」「リファクタ」「設計から」「ちゃんと作る」は開発
2. 言葉に無ければ、Issue の Type / ラベル、ブランチ名（`hotfix/*` は緊急復旧。`feature/*` だけでは決めない）、リポジトリが本番運用中かどうかで決める
3. それでも決まらないときは運用改修を既定にし、仮定を 1 行で伝える。読み違えても差分が小さく、戻しやすい。読み違えると作業が大きく変わるときだけ `AskUserQuestion` で聞く

モードは依頼ごとに決める。同じセッションでも依頼が変われば決め直す。ユーザーがモードを指定したら、それに従う。

## モードごとの作業範囲

- 運用改修: 頼まれた箇所だけ直す。既存のパターンに合わせ、アンチパターンに見えても構造を変えない。周辺のリファクタ・命名変更・テストやドキュメントの追加・依存の更新は作業に含めず、気づいた点として 1 行の提案に留める。変更するファイル数と行数を最小にする
- 緊急復旧: まず復旧する（ロールバック・設定の戻し・最小のパッチ）。原因の深掘りと恒久対応は復旧を確かめた後に分け、別 Issue の提案として出す。復旧の手順は 1 手ずつ結果を確かめて進める
- 開発: ベストプラクティス（設計原則・テスト・保守性）を踏まえる。ただし予定との兼ね合いで取捨選択し、範囲を広げる案は実行せず提案して判断を仰ぐ。既存コードの改善は依頼の範囲に入るものだけ行う

どのモードでも、依頼に無い作業を「ついでに」実行しない。やったほうがよいと思うことは提案に書く。

## 着手前の宣言

ツールで変更を始める前に、次の 3 行を通常テキストで出す。委譲判断（`task-delegation` スキル）と並べて出してよい。

```
作業モード: 運用改修（根拠: 「最小で直して」/ 本番運用中のリポジトリ）
触る範囲: src/foo.go の関数 Bar の条件式だけ（約 5 行）
見送るもの: 周辺の重複ロジックの整理（別 Issue で提案）
```

読み取り専用の調査や質問への回答では省いてよい。プランモードの計画書にも、同じ 3 行を先頭に書く。
