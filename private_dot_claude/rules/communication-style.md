# Communication Style

報告・回答・説明の組み立て方。日本語文の書き方は `easy-japanese.md`、質問の出し方は `question-blocking.md`。

## 報告・回答の型

- 先頭に結論を 1 行。続けて表か箇条書きで全体像。補足が要るものだけ後段で説明する
- 説明の冒頭で「何の話か」を明示する。主語と前提を省かない
- 技術的な話は日常語で要点を伝え、用語や構造の詳細は後から補足する。実装語彙（AWS 用語・設計パターン名）は主役にせず、一般語で説明してから「技術用語では〇〇と呼ぶ」と添える。例: Presigned URL → 事前に署名された通行手形の URL
- 問題の説明は「何が起きているか / なぜか / どうすればよいか」の 3 点で組む
- 完了報告は数行に収める。途中で出した表やコマンド例を繰り返さない。詳細は求められてから出す
- ユーザーが「わからない」と言ったら、抽象度を下げて具体例で言い直す

## 番号・記号・内輪語

- Issue / PR 番号、Step 番号、章節番号は、番号だけで出さず「何を指すか」を言葉で添える。例: 「#320」ではなく「SpecDD 移行の Epic（#320）」
- GitHub の Issue / PR 番号は、報告・表・箇条書きのどこに出ても Markdown リンクにする。Issue は `/issues/`、PR は `/pull/`。書く前にどちらかを確かめる。例外は `AskUserQuestion` の `label` / `description` だけ（プレーンテキストで表示されるため）。そこでは番号に短い説明を添える
- セッション運用で生まれた内輪語（窓 / 波 / レーン / 枠 / HQ など）や作業グループのコードネームをユーザー向けの文に使わない。一般語で書くか、初出で 1 行の定義を添える

## 質問・選択肢・方針

- 質問や選択肢の前に、なぜその判断が必要かを 1 文で説明する
- 方針を述べたら、それと矛盾する別案を続けて出さない。例外や補足は方針と区別して書く
- 設計の選択肢は「比較表 → 選択 → 詳細」の順。まず比較表だけを出し、選ばれてから詳細を展開する。比較表は 3 列まで、セルは短い語句。長文の比較は表をやめて案ごとに見出しと箇条書きにする
- 判断を求める場面は `AskUserQuestion` を使う（`question-blocking.md`）

## 作業の節目のサマリ

`AskUserQuestion` の直前、長いサブタスクの完了時、方針転換時には、3〜5 行で現状を書く: スコープ / 直近の進捗 / 残作業と次の一手。

## Issue / PR / ADR の起票ドラフト

ターミナルに本文をベタ書きしない。タイトル案・属性（Type / SP / Priority / 親 Epic / Labels）・目的 1〜2 行・検討範囲と AC の見出し・スコープ境界・関連 Issue をサマリで示し、構成の了承を得てから本文を生成して起票する。

## 不満サインへの対応

「同じ話」「意味がわからない」「論点を外している」「長い」「いえ、ちがう」などの言葉が出たら、論点を外している前提で立て直す。

1. 短く謝る
2. ユーザーの問いを 1 文で言い直して確認する
3. 合っていれば結論 1〜2 文で答え直す
4. 認識がずれた理由を 1 文だけ添える
