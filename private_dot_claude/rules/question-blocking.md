# Question Blocking Rule

## 大原則: 判断が必要な場面では質問モードを使う（最重要・繰り返し指摘されている）

**ユーザーの判断が要る場面では、通常テキストで問いかけず `AskUserQuestion`（質問モード）を使う。**
これは繰り返し指摘されている規範であり、「今回は文章で聞くほうが自然」と自分で例外を作らない。

- **対象**: 方針の選択・設計案の採否・スコープの決定・マージや外向き操作の可否・
  前提が変わったときの進め方など、**ユーザーが決めないと先へ進めないもの全般**
- **なぜ**: 通常テキストで問うと入力がブロックされ、ユーザーは Esc を押す必要が出る。
  さらに問いがログに流れて見落とされる。質問モードなら選択肢がその場に残り、答えやすい
- **やり方**: 質問モードを呼ぶ**直前の通常テキスト**で、判断に必要な文脈（何の話か・
  なぜ判断が要るか・比較表・Issue/PR のリンク）を先出しし、そのうえで `AskUserQuestion` を呼ぶ。
  選択肢の `label` / `description` に URL や Markdown リンクを書かない
  （詳細は [`communication-style.md`](./communication-style.md)）
- **推奨案があるときは、それを先頭の選択肢にし `（推奨）` を付ける**

### 質問モードを使わなくてよい場面

- 自明・コードやドキュメントで確認できる・慣習的なデフォルトがある → そもそも質問せず進める
- ユーザーが事前に「任せる」「適当に進めて」と明示的に委任した
- 判断ではなく**報告**（完了報告・進捗共有）。これは通常テキストでよい

### アンチパターン

- 通常テキストの末尾に「A と B のどちらにしますか？」と書いて次のターンを待つ
- 「お返事待ちです」と書いて作業を止める（待つなら質問モードで待つ）
- 判断を要する論点を報告文の中に埋め込み、質問として立てない


`AskUserQuestion`（質問モード）でユーザーに質問を出したら、**ユーザーが回答するまで待つ**。これは最重要かつブロッキングの規範であり、時間がかかっても待ち続ける。

## 原則

- 質問モードで質問を出す = 「ユーザーの回答が来るまで処理をブロックする」意図。回答を得ずに次の作業へ進めない。
- ハーネスが `No response after Ns — the user may be away from keyboard. Proceed using your best judgment ...` のようなタイムアウトを返しても、**それを「離席したので省略・自己判断してよい」という許可と解釈しない**。ユーザーは「時間がかかっても必ず答える」と明言している。
- タイムアウトが返ってきた場合の正しい振る舞い:
  - best judgment で作業を進めない。
  - ユーザーの回答を待っている状態であることを短く伝える（または黙って待つ）。回答が来てから続行する。
  - 待っている間に、質問と無関係で安全な準備作業（読み取り専用の下調べ等）を進めるのは可。ただし質問の答えに依存する判断・変更・外向き操作には着手しない。

## やってはいけないこと（アンチパターン）

- タイムアウトを口実に「best judgment でデフォルト選択肢を選んで進める」
- 「離席していると判断して勝手に決めた、違えば後で巻き戻す」と称して、コミット・push・PR 作成・マージ・デプロイ等の**外向き・不可逆に近い操作**まで実行する
- タイムアウト後に AskUserQuestion を再送せず、暗黙に自分で決める

## 例外

- ユーザーが事前に「判断は任せる」「適当に進めて」「デフォルトで」等と**明示的に**委任した場合のみ、デフォルトを選んで進めてよい。
- そもそも質問が不要（自明・コードやドキュメントで確認可能・慣習的なデフォルトがある）なら、質問モードを使わずに進める。これは本ルールと矛盾しない（本ルールは「質問モードを使ったら待つ」を縛るのであって、「何でも質問しろ」ではない）。
